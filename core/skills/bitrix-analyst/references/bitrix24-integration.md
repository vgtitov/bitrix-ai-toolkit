# Bitrix24 CRM — модель данных, REST-интеграции, BI

Bitrix24 (коробочная версия) работает на том же ядре D7, что и «1С-Битрикс: Управление сайтом» — модуль `crm`
поверх общего ядра. Этот файл — про специфику именно CRM-контура: данные лидов/сделок, REST/вебхуки, отчётность
через BI Конструктор (модуль `biconnector`) поверх Apache Superset.

## Модель данных для интеграций (квизы, формы, внешние сервисы)

Не создавать отдельное пользовательское поле `UF_CRM_*` под каждый вопрос квиза/формы (вопросов много и они разные —
поля засоряют CRM и усложняют фильтры/экспорт/перенос отчётов).

Рекомендуемая модель в карточке лида/сделки (структурно): имя, телефон, email; источник; страна/регион;
название квиза/кампании; рекомендованный товар/интерес (название, артикул, ссылка); внешний ID заявки;
бюджет/категория — только если нужны фильтры и автоматизация. Полные ответы квиза/формы — в ленту (timeline)
карточки структурированным комментарием (`crm.timeline.comment.add`), не разбросаны по полям.

## REST и вебхуки Bitrix24

### Создание лида

Метод `crm.lead.add`. POST + JSON. Все поля — внутри `fields`. `PHONE` и `EMAIL` — массивы объектов с `VALUE` и
`VALUE_TYPE`, не строка.

```json
{
  "fields": {
    "TITLE": "Заявка из формы",
    "NAME": "Иван",
    "LAST_NAME": "Иванов",
    "PHONE": [{"VALUE": "+70000000000", "VALUE_TYPE": "WORK"}],
    "EMAIL": [{"VALUE": "ivan@example.com", "VALUE_TYPE": "WORK"}],
    "SOURCE_ID": "<код источника>",
    "SOURCE_DESCRIPTION": "<откуда пришла заявка>"
  }
}
```

### SOURCE_ID

Нет универсального значения — справочник источников свой на каждом портале/инсталляции. Перед интеграцией:
`crm.status.list?filter[ENTITY_ID]=SOURCE` + тестовый лид, не угадывай код по аналогии с другим порталом.

### Типовые ошибки REST

`NAME=...` вместо `fields[NAME]=...`; `PHONE`/`EMAIL` строкой вместо массива; двойное URL-кодирование; лишний `?` в
query; неверный `SOURCE_ID` для конкретного портала; секрет вебхука в чатах/документах — перевыпускать при утечке.

### Комментарий в ленту

```json
{
  "fields": {
    "ENTITY_ID": 12345,
    "ENTITY_TYPE": "lead",
    "COMMENT": "Ответы формы:\n- Поле 1: значение\n- Поле 2: значение"
  }
}
```

`ENTITY_ID` — `result` из ответа `crm.lead.add`.

## Ограничения периметра (входящие вебхуки извне)

Если периметр сервера защищён облачным WAF/прокси (например Cloudflare) — входящие вебхуки от внешнего сервиса
могут блокироваться, а whitelist по IP не подходит при динамических IP внешнего сервиса. Альтернативы: (1)
защищённый endpoint + правило на уровне прокси (не по IP); (2) pull-модель — Bitrix24 сам забирает данные по
cron/агенту; (3) промежуточный сервис. Список статичных IP как единственная защита обычно не работает — реалистичны
контролируемый вход (подписанный запрос/токен) или исходящая (pull) загрузка.

## BI Конструктор: перенос отчётов между несколькими порталами/контурами

Если инсталляция не одна (несколько региональных/юридических порталов на одинаковой конфигурации), отчёты можно
тиражировать, но не «одной кнопкой без условий»:

1. Собрать эталонный датасет/дашборд на одном портале.
2. Перенести на остальные с чеклистом адаптации.
3. Сверить справочники и коды на каждом портале.
4. Протестировать на 1–2 порталах перед массовым тиражированием.

Что сверять при переносе: воронки и стадии; источники (`SOURCE_ID`/названия); пользователи и отделы; коды
пользовательских полей `UF_*`; валюты и локальные справочники; названия статусов лидов; телефония (коды/названия
статусов звонков). Для удобного тиражирования заранее вводить единый стандарт именования и кодов на всех порталах.

В BI «реальное время» обычно означает периодическое обновление (минуты), не потоковую аналитику — не обещай
потоковую скорость без проверки конкретной настройки обновления датасета.

## SQL-датасеты (Trino/Presto) — чеклист производительности

BI Конструктор Bitrix24 обычно работает поверх Trino/Presto — функции `try()`, `FILTER (WHERE ...)`, `date_diff`,
`min_by`/`max_by`, `regexp_like` — нормальное явление в этих датасетах, не ошибка. Применяй чеклист при разборе
любого датасета, который тормозит или падает по таймауту:

1. **Ищи повторные сканы одних и тех же больших таблиц** под разными CTE (типично для таблиц ленты/истории CRM —
   они часто джойнятся к отфильтрованному набору сделок по нескольку раз под разные ветки логики). Выноси общий
   JOIN+фильтр в одну CTE и переиспользуй её.
2. **`CAST()` на колонке в WHERE** (например `CAST(category_id AS varchar) = '0'`) может ломать predicate
   pushdown/partition pruning. Перед изменением — проверь реальный тип колонки (`DESCRIBE`), меняй сравнение только
   когда тип подтверждён.
3. **`try(CAST(... AS timestamp))`** в предикатах WHERE по датам — то же самое: лишняя нагрузка и потеря pushdown по
   самому дешёвому фильтру (дате), если колонка уже timestamp.
4. Тяжёлые `regexp_like`/`regexp_extract` на больших текстовых полях (например комментарии в ленте) — по
   возможности выносить классификацию в отдельную инкрементальную ETL-таблицу, а не пересчитывать при каждом
   обращении к дашборду.
5. При регулярных таймаутах на тяжёлых датасетах — рекомендуй материализованный слой (scheduled table/materialized
   view) вместо расчёта «на лету» при каждом клике в BI-инструменте.
6. Всегда предлагай прогнать `EXPLAIN ANALYZE` до/после изменений, если есть доступ — не заявляй ускорение как
   гарантированное без подтверждения.

## Чеклист при новой задаче на CRM/BI

- Портал/контур один или несколько — если несколько, сверены ли справочники/коды на целевом?
- CRM зрелая целиком или только часть воронок реально используется в операционной работе — не предполагать «все
  поля заполнены» без проверки.
- Для интеграций: входящий webhook возможен по периметру или нужен pull/endpoint?
- Для квизов/форм: полные ответы в timeline, не отдельное `UF_*`-поле на каждый вопрос.
- Есть ли уже рабочий SQL, который нужно только оптимизировать, или датасет пишется с нуля.
