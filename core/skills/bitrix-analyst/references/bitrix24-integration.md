# Bitrix24 CRM — модель данных, REST-интеграции, BI

Коробочный Bitrix24 работает на том же ядре D7, что и «1С-Битрикс: Управление сайтом» — модуль `crm` поверх
общего ядра, код доступен. В облачном Bitrix24 кода нет: только REST/вебхуки, приложения и штатные настройки. Сначала
выясни, какой у заказчика портал, — от этого зависит весь набор решений. Этот файл — про специфику CRM-контура:
данные лидов/сделок, REST/вебхуки, отчётность через BI Конструктор (модуль `biconnector`) поверх Apache Superset.

## Модель данных для интеграций (квизы, формы, внешние сервисы)

Не создавать отдельное пользовательское поле `UF_CRM_*` под каждый вопрос квиза/формы по умолчанию (вопросов много
и они разные — поля засоряют CRM и усложняют фильтры/экспорт/перенос отчётов). Сначала раздели ответы по назначению:

- **нужно фильтровать, считать в отчётах, запускать по нему автоматизацию** — отдельное поле (стандартное или
  `UF_*`): имя, телефон, email; источник; страна/регион; квиз/кампания; интерес (товар, артикул, ссылка); внешний ID
  заявки; бюджет/категория;
- **нужно только прочитать менеджеру** — в ленту (timeline) карточки структурированным комментарием
  (`crm.timeline.comment.add`). По тексту комментария не фильтруют, не валидируют и не строят автоматизацию.

Персональные данные из ответов (документы, здоровье, дети и т.п.) не пиши ни в поля, ни в ленту без решения, кто и
зачем их хранит.

## REST и вебхуки Bitrix24

### Создание лида

Метод `crm.lead.add` (для новых интеграций документация Bitrix24 рекомендует универсальный `crm.item.add` —
проверь, что принято на портале). Пример ниже — POST + JSON; все поля — внутри `fields`. `PHONE` и `EMAIL` — массивы
объектов с `VALUE` и `VALUE_TYPE`, не строка.

```json
{
  "fields": {
    "TITLE": "Заявка из формы",
    "NAME": "<имя>",
    "LAST_NAME": "<фамилия>",
    "PHONE": [{"VALUE": "<телефон>", "VALUE_TYPE": "WORK"}],
    "EMAIL": [{"VALUE": "<email>", "VALUE_TYPE": "WORK"}],
    "SOURCE_ID": "<код источника>",
    "SOURCE_DESCRIPTION": "<откуда пришла заявка>"
  }
}
```

### SOURCE_ID

Нет универсального значения — справочник источников свой на каждом портале/инсталляции. Перед интеграцией:
`crm.status.list?filter[ENTITY_ID]=SOURCE` + тестовый лид, не угадывай код по аналогии с другим порталом.

### Типовые ошибки REST

`NAME=...` вместо `fields[NAME]=...`; `PHONE`/`EMAIL` строкой вместо массива; двойное URL-кодирование; лишний `?` в
query; неверный `SOURCE_ID` для конкретного портала; секрет вебхука в чатах/документах — перевыпускать при утечке.

### Комментарий в ленту

```json
{
  "fields": {
    "ENTITY_ID": 12345,
    "ENTITY_TYPE": "lead",
    "COMMENT": "Ответы формы:\n- Поле 1: значение\n- Поле 2: значение"
  }
}
```

`ENTITY_ID` — `result` из ответа `crm.lead.add`.

## Безопасный приём входящих вебхуков

Если периметр защищён WAF/прокси (например Cloudflare), входящие вебхуки внешнего сервиса могут блокироваться, а
whitelist по IP не подходит при динамических IP. Защиту **не отключают и не делают широких исключений** — выбирают
один из вариантов:

1. **Отдельный endpoint с проверкой подлинности**: обязательно HMAC-подпись тела запроса общим секретом, метка
   времени и одноразовый идентификатор (nonce) против повтора, ограничение частоты. Статический токен в заголовке
   тело не подписывает — он допустим только в дополнение к подписи. Исключение в WAF — только на этот путь.
2. **Pull-модель**: портал сам забирает данные у сервиса по расписанию (агент/cron) — входящий трафик не нужен.
3. **Промежуточный сервис**, который принимает вебхук, проверяет подпись и кладёт данные в Bitrix24 через REST.

Секреты вебхуков не держать в коде, логах, чатах и документах; утёк — перевыпустить.

## BI Конструктор: перенос отчётов между несколькими порталами/контурами

Если инсталляция не одна (несколько региональных/юридических порталов на одинаковой конфигурации), отчёты можно
тиражировать, но не «одной кнопкой без условий»:

1. Собрать эталонный датасет/дашборд на одном портале.
2. Перенести на остальные с чеклистом адаптации.
3. Сверить справочники и коды на каждом портале.
4. Протестировать на 1–2 порталах перед массовым тиражированием.

Что сверять при переносе: воронки и стадии; источники (`SOURCE_ID`/названия); пользователи и отделы; коды
пользовательских полей `UF_*`; валюты и локальные справочники; названия статусов лидов; телефония (коды/названия
статусов звонков). Для удобного тиражирования заранее вводить единый стандарт именования и кодов на всех порталах.

В BI «реальное время» обычно означает периодическое обновление (минуты), не потоковую аналитику — не обещай
потоковую скорость без проверки конкретной настройки обновления датасета.

## SQL-датасеты (Trino) — чеклист производительности

SQL в BI Конструкторе Bitrix24 пишется на диалекте Trino — функции `try()`, `FILTER (WHERE ...)`, `date_diff`,
`min_by`/`max_by`, `regexp_like` — нормальное явление в этих датасетах, не ошибка. Применяй чеклист при разборе
любого датасета, который тормозит или падает по таймауту:

1. **Ищи повторные сканы одних и тех же больших таблиц** (типично для таблиц ленты/истории CRM — их джойнят к
   отфильтрованному набору сделок по нескольку раз под разные ветки логики). Вынос в CTE сам по себе **не
   гарантирует** выигрыша: Trino подставляет CTE в каждое место использования, и скан может повторяться —
   проверяй по плану. Помогает собрать
   разные ветки в один проход — условная агрегация (`count(*) FILTER (WHERE ...)`, `max_by`) по одному JOIN вместо
   нескольких подзапросов, либо вынести тяжёлую часть в отдельный заранее рассчитанный датасет.
2. **`CAST()` на колонке в WHERE** (например `CAST(category_id AS varchar) = '0'`) может ломать predicate
   pushdown/partition pruning. Перед изменением — проверь реальный тип колонки (`DESCRIBE`), меняй сравнение только
   когда тип подтверждён.
3. **`try(CAST(... AS timestamp))`** в предикатах WHERE по датам — то же самое: лишняя нагрузка и потеря pushdown по
   самому дешёвому фильтру (дате), если колонка уже timestamp.
4. Тяжёлые `regexp_like`/`regexp_extract` на больших текстовых полях (например комментарии в ленте) — по
   возможности выносить классификацию в отдельную инкрементальную ETL-таблицу, а не пересчитывать при каждом
   обращении к дашборду.
5. При регулярных таймаутах на тяжёлых датасетах — предложи вынести расчёт из датасета «на лету»: отдельный
   предрасчитанный набор (выгрузка/ETL вне BI) вместо пересчёта при каждом открытии дашборда. Материализованные
   представления и плановые таблицы средствами самого BI Конструктора документацией не подтверждены — не обещай их.
6. Замеряй до и после штатными средствами BI Конструктора (SQL Lab): `bitrix24.bi_queries_t()` — история запросов
   с временем выполнения, объёмом и статусом кэша; `bi_explain_query()` — план выполнения конкретного запроса по его
   `QUERY_ID` и времени. Не заявляй ускорение как гарантированное без замера.

## Чеклист при новой задаче на CRM/BI

- Портал/контур один или несколько — если несколько, сверены ли справочники/коды на целевом?
- CRM зрелая целиком или только часть воронок реально используется в операционной работе — не предполагать «все
  поля заполнены» без проверки.
- Для интеграций: входящий webhook возможен по периметру или нужен pull/endpoint?
- Для квизов/форм: разделены ли ответы на «для фильтров/отчётов/автоматизации» (поля) и «только прочитать»
  (timeline); нет ли среди ответов персональных данных, которые не надо хранить.
- Есть ли уже рабочий SQL, который нужно только оптимизировать, или датасет пишется с нуля.
