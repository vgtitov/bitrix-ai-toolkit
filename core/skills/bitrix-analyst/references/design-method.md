# Методология проектирования доработки под Битрикс

## Шаг 1. Требования — в терминах поведения, не реализации
Обязательные вопросы (не заданы → проектировать рано):
- кто пользователь сценария и что он хочет получить;
- что происходит **сейчас** (as-is), что должно (to-be);
- **объёмы** (сколько элементов/заказов/хитов) — это выбирает архитектуру: инфоблок vs highload vs внешнее хранилище;
- **персонализация**: зависит ли вывод от пользователя/региона/типа цены → влияет на кэш и композит;
- интеграции: 1С (CommerceML, ключ `XML_ID`), платёжки, CRM, склады;
- крайние случаи: пусто, дубли, отказ внешнего сервиса, **повторная доставка вебхука**;
- кто и как проверит, что готово.

## Шаг 2. Критерии приёмки — проверяемые (Given/When/Then)
> *Given* товар с остатком 3, *When* пользователь добавляет 5 в корзину, *Then* в корзину попадает 3, показывается
> «Доступно только 3 шт.», в лог пишется warning, заказ не создаётся.

Плохо: «корректно обрабатывать остатки».

## Шаг 3. Impact analysis — чек-лист под Битрикс
- [ ] какие **модули** ядра затронуты: `main` / `iblock` / `catalog` / `sale` / `highloadblock`;
- [ ] какие **сущности данных**: инфоблоки, свойства, HL-блоки, свои таблицы, пользовательские поля;
- [ ] **уже реализованное** — искать в ОБОИХ слоях (`/local` и `/bitrix/modules`, приоритет `/local`) + marketplace;
- [ ] **старое ядро или D7**: есть ли нужный метод в D7 в ВАШЕЙ версии (по реальному коду ядра, не по `api_d7`);
- [ ] **производительность**: новые запросы в списочных выборках? N+1? нужен кэш и по каким тегам сбрасывается?
      не ломается ли композит (персонализация)?
- [ ] **кэш**: какие ключи инвалидируются, не утечёт ли приватное между пользователями/регионами;
- [ ] **обновляемость**: правки только в `/local`? копируем компонент — зафиксировали версию оригинала?
- [ ] **обмен с 1С**: не ломается ли сопоставление по `XML_ID`, переживёт ли следующую выгрузку;
- [ ] **права и роли**: кто имеет доступ, проверяется ли;
- [ ] **идемпотентность**: событие/агент/вебхук может прийти дважды;
- [ ] **миграции**: структура — только `sprint.migration`, откат описан;
- [ ] **обратная совместимость**: старые ссылки, старые заказы в БД, данные без нового свойства;
- [ ] **риски и как проверим на бою**.

## Шаг 4. Выбор точки расширения — дерево решений
Идти сверху вниз, останавливаться на первом подходящем:

| # | Точка | Когда | Цена |
|---|---|---|---|
| 1 | **`result_modifier.php` / `component_epilog.php`** | доработать данные типового компонента для вывода | ~0, обновляемо |
| 2 | **Событие ядра** (`EventManager`, ORM-события, события `sale`) | вклиниться в процесс: цена, статус, письмо, выгрузка | низкая, обновляемо. ⚠️ рекурсия и порядок обработчиков |
| 3 | **Свой компонент** в `/local/components` | нужен свой вывод/выборка, типовой не подходит по сути | средняя |
| 4 | **Копия типового** в `/local/components` | типовой на 90% + правки внутри логики | средняя; форк **не получает фиксов вендора** — записать версию-источник и причину |
| 5 | **Свой модуль** `/local/modules/vendor.name` | своя предметная область: таблицы, настройки, права, установка, переносимость | высокая, окупается вдолгую |
| 6 | **Правка `/bitrix/modules`** | **никогда** | потеря при обновлении; вынужденно (баг ядра) → патч в реестре + `core_modified = true` |

Доп. критерий: *«если завтра выйдет обновление продукта — что сломается?»* Для вариантов 1–3 ответ должен быть «ничего».

## Шаг 5. ADR — если решение трудно откатить / затрагивает многих / выбирали из вариантов
Шаблон — `adr-template.md`.

## Шаг 6. Обратная совместимость и план миграции
- изменение структуры — **всегда обратимая** миграция (`up`/`down`);
- **expand → migrate → contract**: сначала добавить новое, потом перевести потребителей, потом удалить старое;
- на бою — **двойная запись + feature-флаг** (`Option::get`), а не «выкатили и молимся»;
- удаление старого кода — **отдельная задача**, иначе не произойдёт никогда;
- техдолг фиксируется явно (ADR + трекер), а не `// TODO потом`.

## Что аналитик обязан приложить к ЧТЗ
1. Поведение (сценарии + крайние случаи). 2. Модель данных (что где, ключи, связи, объёмы). 3. Критерии приёмки.
4. Точка расширения + обоснование. 5. Impact-чеклист с отметками. 6. Риски + план отката. 7. ADR (если архитектурное).

## Что проверить по РЕАЛЬНОМУ ядру, а не по памяти
`ServiceLocator` и автоварайринг (`main/lib/di/servicelocator.php`) · читается ли `services` из `.settings_extra.php`
· полнота D7 ORM для нужной сущности (часть `sale`/`catalog` только через `C*`) → `legacy_required` в version-stack
· наличие `Diag\FileLogger` и `psr/log` в сборке · сигнатуры `Main\Engine\Controller` · наличие сгенерированных
ORM-классов инфоблоков (`Bitrix\Iblock\Elements\Element<Code>Table` — есть не всегда).
