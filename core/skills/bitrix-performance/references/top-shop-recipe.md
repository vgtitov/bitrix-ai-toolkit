# Рецепт быстрого Битрикс-магазина — слои и пороги (обезличенно)

Скорость топового магазина — не одна фича, а **слоёный пирог кэша**, где 90%+ хитов не доходят до PHP/MySQL.
Наблюдения на публичных страницах крупных каталогов + Intervolga/Битрикс. Пороговые цифры — зашивать в ревью.

## Слои кэша (снизу вверх)
1. **Composite site** — HTML-скелет в статфайл `/bitrix/html_pages/`, отдаётся **напрямую nginx мимо PHP** (TTFB единицы мс).
   Динамика (корзина, город, авторизация) — одним AJAX. HTML помечен `no-cache` (персональный скелет), но сервер отдаёт мгновенно.
   TTL под частоту обновления (до 86400с). **Поднять лимит композит-кэша со 100 МБ (дефолт) до нескольких ГБ** на большом каталоге.
2. **Тегированный кэш** `iblock_id_<ID>` — большой `CACHE_TIME` без протухания (сброс только изменённого инфоблока).
3. **Компонентный кэш** каждого штатного компонента (комбинировать с тегами, не ставить мелкий TTL).
4. **Хранилище кэша и сессий — Redis** (не файлы), общий на веб-кластер. OPcache (`validate_timestamps=0` на проде).

## Каталог — пороги деградации (ЗАШИТЬ в ревью/аудит)
- **Инфоблоки 2.0 обязательны от ~50 000 товаров**; свойств держать **< 50**. На 1.0 всё в EAV `b_iblock_element_property`
  (каждое свойство удваивает время). На 2.0 — плоская `b_iblock_element_prop_s<ID>`, **вешать свои MySQL-индексы** под фильтры.
- **Фасетный индекс** умного фильтра — денормализованная таблица, отвечает мгновенно. **Деградирует ~10 млн записей фасета**
  (предупреждать на ~7 млн, за 30%). Объём: `разделы × (товары × свойства) + (SKU × (свойства SKU + типы цен))`.
  Генерация: 50K товаров ≈ 50 мин, 100K ≈ 1.5ч (фоново, не в бою).
- **Список без фасета:** 50K товаров ~10.4с, 100K ~32.7с; с фасетом — десятые доли секунды.
- **Типы цен дороги: каждый +5-10% нагрузки, максимум 10-20.** Склады до ~50 — безопасно (`b_catalog_store_product` масштабируется).
- Редкие/технические характеристики — в **highload-блоки**, не в свойства инфоблока.
- **Ключ кэша каталога включает регион + тип цены** (иначе кэш «протекает» между городами).

RPS-эффект (замеры Intervolga): 10K ИБ1.0 без фасета — 25.9 · 50K фасет+ИБ1.0 — 15.6 · 50K ИБ2.0 — 22.5 · 100K ИБ2.0 — 14.2.

## Поиск
Штатный (`b_search_content_stem`): 50K товаров ≈ **29 млн строк**, холодный запрос **600-1000 SQL / ~8с**. При **1M+ SKU**
выносить в **Elastic/OpenSearch/Meilisearch**, автоподсказки — отдельным лёгким JSON-эндпоинтом. Мониторить размер стем-таблицы.

## Инфра/фронт
- nginx впереди (часто + edge-WAF/CDN), отдаёт статику и композит-HTML мимо PHP-FPM.
- **HTTP/2** норма (h3 — точка роста); **gzip есть, brotli недокручен даже у крупных** (−15-20% текста).
- Статика: долгий `max-age` (30 дней) + `ETag`, **версия ассета в query-string** (инвалидация без сброса кэша браузера).
- **webp/avif** + `resize_cache` + ленивая загрузка (`IntersectionObserver`/`data-src`) — крупный рычаг LCP.
- **Веб-кластер** при высоком RPS: несколько нод + общий Redis + репликация БД + сессии в Redis.

## Внешние обёрточные слои крупного магазина (не чисто-Битрикс)
- **Внешний поиск/рекомендации** (Elastic / SaaS) — не искать баг «в поиске Битрикс», если поиск не Битрикса.
- **CDN/edge-прокси** (Cloudflare и др.) — влияет на отладку (кэш-заголовки, «почему не видно изменений»), композит, WAF.
- **Битрикс24-CRM/омниканал** (лид-формы, Открытые линии, чат) — отдельная интеграция.
- **1С-обмен CommerceML** — товары/ТП/цены/остатки/заказы; XML_ID = GUID из 1С как ключ сопоставления.
- **dataLayer/аналитика** (GTM/GA/Метрика/пиксели, e-commerce события).

## Что зашить в toolkit (автопроверки ревью)
Статически (ast-grep/PHPStan, см. `core/linters/ast-grep/` (в репозитории toolkit)):
1. Каталожный компонент с малым `CACHE_TIME` без тега `iblock_id_*` → «поставь тегированный кэш».
2. `CACHE_TYPE=>'N'` в каталожных компонентах → ошибка ревью.
3. N+1 (GetList/GetProperty в цикле), `GetNext()` без лимита → риск полного скана.
4. Логика, ломающая композит: вывод персональных данных (имя/город/корзина) в кэш-зоне без динамической области.
5. Ключ кэша без региона/типа цены там, где выборка от них зависит.
Инварианты инфры (чек-лист аудита / CI): композит вкл. и через nginx · `cache.type=redis` · композит-лимит >100 МБ ·
OPcache `validate_timestamps=0` · nginx brotli+expires+h2 · алерт на размер фасета ~7 млн и стем-таблицы поиска.
Порог-скрипт: читать метаданные инфоблоков (`b_iblock_property`: число свойств, версия 1.0/2.0) и размеры таблиц из БД —
ловить деградацию ДО пользователя.
