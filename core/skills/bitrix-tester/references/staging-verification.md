# Проверка данных на стейджинге — что реально лежит в БД / что видит пользователь

Отдельная ось от «ведёт ли себя код правильно»: здесь вопрос — «что реально произошло с данными»
(оформился ли заказ, применилась ли миграция инфоблока, обновилась ли цена). Не изобретай доступ
вручную каждый раз — используй воспроизводимый путь ниже.

## Поднять окружение
- `docker/docker-compose.yml` toolkit (+ `docker/README.md`) — если проект использует
  bitrixdock-совместимый образ. `demo/SETUP.md` — минимальный демо-стенд toolkit для проверки
  самих проверок (не для проверки бизнес-логики проекта).
- Реальный стейджинг проекта — адрес и доступ фиксируй в `local/` (см. «Локализация» в
  `SKILL.md`), не спрашивай заново на каждой задаче.

## Проверить результат миграции (инфоблоки/HL/свойства/права)
Точная команда статуса миграций зависит от установленной версии раннера (`sprint.migration` или
другой) и того, как он подключён в проекте (консольный скрипт vs агент Битрикс) — **`[проверить]`
по факту проекта**, зафиксировать найденную команду в `local/` при первом использовании, не
гадать заново каждый раз. Если раннера нет вообще — сверяй ожидаемую структуру (новое
свойство/HL-блок/секция) напрямую: через админку Битрикс (`/bitrix/admin/`) или запросом к БД на
стейджинге, не на проде.

## Проверить, что заказ/сущность реально создались
```sql
-- пример: последний заказ по стейджинг-БД (адаптируй под структуру b_sale_order/D7 sale)
SELECT ID, STATUS_ID, PRICE, DATE_INSERT FROM b_sale_order ORDER BY ID DESC LIMIT 5;
```
Через D7 (предпочтительно, если есть shell-доступ к PHP на стейджинге):
```php
$order = \Bitrix\Sale\Order::load($orderId);
var_dump($order->getField('STATUS_ID'), $order->getPrice());
```
**Не гадай по интерфейсу «вроде оформилось»** — сверяй фактическую запись в БД/через D7-объект.

## Панель отладки и логи как источник факта
- Панель отладки внизу страницы (для админа на стейджинге) — число SQL-запросов, ошибки,
  предупреждения за конкретный хит.
- Путь error_log — проектный (см. `local/` или `.settings.php` → `exception_handling`); grep по
  времени прогона, не по всему файлу.
- Если ошибка не воспроизводится в панели отладки, но видна пользователю — проверь, не кэш ли это
  (см. `core/skills/bitrix-performance/references/caching.md`): холодный/тёплый кэш даёт разное
  поведение на одной и той же странице.

## Обезличивание
Реальные email/телефон/состав заказа клиента с прод-копии — обезличивай (замени на тестовые
значения) перед тем, как класть выборку в отчёт, тикет или показывать вовне. Прод-копию БД для
проверки данных — только если это разрешено регламентом проекта и ИБ; иначе проверяй на
синтетических данных стейджинга.
