# Репликация и масштабирование — веб-кластер Битрикс

## Master-slave репликация
- Стандартная схема под нагрузку: один master (запись), одна/несколько read-реплик. Настройка
  средствами СУБД (binlog + `CHANGE MASTER TO`/`CHANGE REPLICATION SOURCE TO` в новых версиях).
- **Задержка репликации** — главный источник багов «сохранил — не вижу»: если приложение читает
  сразу после записи с реплики, а репликация отстаёт, пользователь не увидит только что созданный
  заказ/изменение. Диагностика: `SHOW SLAVE STATUS\G` (`Seconds_Behind_Master`,
  `Slave_IO_Running`/`Slave_SQL_Running` должны быть `Yes`).
- Митигация задержки — не «просто подождать»: разделять запросы по чувствительности — сразу после
  записи в рамках того же хита читать с master, не с реплики (Битрикс учитывает это в своих API
  при включённом модуле `cluster`, кастомный код на прямых SQL-запросах — нет, см. ниже). **Важная
  оговорка:** полусинхронная репликация MySQL подтверждает лишь доставку транзакции в relay log
  реплики, а не её применение — она НЕ решает проблему «прочитать только что записанное с реплики»;
  для гарантированно консистентного чтения нужен либо запрос к master, либо ожидание конкретной
  позиции репликации (GTID-based wait), а не просто включённый semi-sync.

## Модуль «Веб-кластер» Битрикс
Битрикс умеет сам распределять read/write между master и слейвами через модуль `cluster` — но это
осознанная настройка, не «поставил реплику — само заработало»: код, читающий сразу после записи в
рамках одного хита, нужно явно направлять на master (Битрикс это учитывает внутри своих API, но
кастомный код на прямых SQL-запросах — нет, см. `bitrix-dev`).

## Секционирование vs шардирование
- Секционирование (PARTITIONING) одной таблицы по диапазону/списку — для очень больших таблиц с
  предсказуемым паттерном очистки/архивации (логи, старые заказы) в рамках одного сервера.
- Шардирование (несколько независимых серверов БД, данные разнесены) — на масштабе, который
  Битрикс-проекты в норме не достигают без крупного кастома; решение архитектурного уровня, не
  рутинная DBA-задача — обсуждать с `bitrix-analyst`/архитектором проекта до внедрения.

## Сайзинг
Число реплик и их размер — от реального профиля чтение/запись (посчитанного по slow log/статусам,
не «на глаз») и требуемого RTO при потере master. Реплика — не бэкап (репликация переносит и
ошибочное DELETE тоже, мгновенно) — держать отдельный регламент бэкапа (`backup-recovery.md`)
независимо от наличия реплик.
