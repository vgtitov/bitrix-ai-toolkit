# Мониторинг и блокировки MySQL/MariaDB под Битрикс

## Базовая диагностика (снять первым делом)
```sql
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW GLOBAL STATUS LIKE 'Slow_queries';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';   -- cache hit ratio считается по ним
SHOW ENGINE INNODB STATUS\G                            -- секция TRANSACTIONS: текущие блокировки, LATEST DETECTED DEADLOCK
SHOW PROCESSLIST;                                       -- зависшие/долгие запросы прямо сейчас
```
**Cache hit ratio** = `1 - (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)`, цель
> 95-99%. Ниже — buffer_pool мал для рабочего набора данных (см. тюнинг в `SKILL.md`) либо
единичный тяжёлый запрос вымыл кэш (проверь по времени совпадение с фоновой задачей/импортом).

## Топ медленных запросов
- Включить slow query log (`slow_query_log=1`, `long_query_time` — порог в секундах, на Битрикс
  обычно 1-2 сек как стартовая точка).
- `pt-query-digest` (Percona Toolkit) или `mysqldumpslow` — агрегация по суммарному времени, не по
  единичному самому долгому запросу (частый быстрый запрос суммарно дороже редкого медленного).
- Найденный тяжёлый запрос — не чинить в СУБД: если это D7 ORM/`GetList` без индекса или N+1,
  фикс уходит в `bitrix-performance`/`bitrix-dev` (уровень приложения).

## Блокировки и deadlock
- Типичное место у Битрикс — `b_sale_order`/`b_sale_basket`/`b_catalog_store_product` под
  конкурентным оформлением заказов и обновлением остатков.
- `information_schema.INNODB_TRX` (MySQL 5.7/старый MariaDB) или `performance_schema.data_locks` +
  `data_lock_waits` (MySQL 8+) — кто кого блокирует, с текстом запроса и временем ожидания.
- Deadlock viewer: последний deadlock — в `SHOW ENGINE INNODB STATUS` секция `LATEST DETECTED
  DEADLOCK`; MySQL сам откатывает одну из транзакций (приложение обязано делать retry на такую
  ошибку — если retry нет, это баг на стороне кода, не только СУБД). Регулярно повторяющийся
  паттерн deadlock — повод проверить порядок захвата блокировок в транзакциях, их длину и наличие
  индексов под условия `WHERE`/`JOIN` (без индекса блокируется больше строк, чем нужно) — «недостаточная
  изоляция» это лишь один из возможных диагнозов, не единственный.
- Снятие зависшего сеанса — сначала проверь, есть ли у него ОТКРЫТАЯ ТРАНЗАКЦИЯ
  (`information_schema.INNODB_TRX`/`performance_schema`): `KILL QUERY <id>` прерывает только текущий
  запрос и не закрывает транзакцию — блокировки, удерживаемые транзакцией, останутся. `KILL <id>`
  (закрывает соединение) запускает откат транзакции, который на большом объёме изменений может идти
  долго и сам по себе нагружать сервер — учитывай это в момент эскалации, не жди мгновенного эффекта.
  Не убивать вслепую все долгие сеансы — сначала посмотреть, что они делают (может быть легитимный
  долгий импорт/бэкап).

## Алерты (что имеет смысл мониторить постоянно)
Threads_connected к max_connections (насыщение пула), cache hit ratio (просадка), число строк в
slow log за интервал (тренд, не абсолютное число), `Seconds_Behind_Master` на репликах (задержка),
свободное место на диске под датадиром (InnoDB не деградирует красиво при 100% диска).
