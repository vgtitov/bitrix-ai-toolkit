# Кастомные изменения ядра Битрикс — как с этим жить

Идеал — правки только в `/local`. Реальность многих проектов — **ядро `/bitrix` уже изменено** (хотфиксы, костыли,
доработки под клиента). Отрицать это бессмысленно; задача — сделать изменения управляемыми и не потерять их при обновлении.

## Правило агента
1. **По умолчанию не трогать ядро.** Новая задача → решение в `/local` (копия компонента, событие, свой класс).
2. **Если ядро уже правлено** — учитывать это: сигнатуры и поведение брать из ФАКТИЧЕСКОГО ядра проекта, не из
   эталонного дистрибутива (иначе выводы будут неверными).
3. **Правка ядра — только осознанно и с человеком**, когда иначе никак (нет точки расширения). Обязательно фиксировать.

## Как фиксировать правки ядра (чтобы не потерять при обновлении)
- **Патчи в git.** Каталог `patches/core/` в репозитории проекта: на каждую правку — `.patch`/`.diff` с описанием
  (что, зачем, дата, задача). Применяются скриптом после обновления продукта.
- **Реестр правок** — `patches/core/REGISTRY.md`: файл ядра · что изменено · причина · задача · автор · дата ·
  «можно ли вынести в /local» (цель — постепенно обнулять список).
- **Диф с эталоном версии.** Держи рядом чистый дистрибутив своей версии ядра и периодически:
  ```bash
  diff -ru /path/vanilla-bitrix/modules /path/project/bitrix/modules > core-diff.txt
  ```
  Так видно ВСЕ фактические расхождения (в т.ч. забытые кем-то).
- **Перед обновлением продукта** — снять свежий диф, после обновления — переприменить патчи и прогнать проверки.

## Настройка toolkit под изменённое ядро
В `config/version-stack.toml`:
```toml
[bitrix]
core_path = "bitrix/modules"     # ФАКТИЧЕСКОЕ ядро проекта (для scanDirectories PHPStan и поиска)
core_modified = true             # ядро правлено — анализ вести по факту, а не по эталону
core_patches = "patches/core"    # где лежат патчи и реестр
```
Следствия:
- **PHPStan `scanDirectories`** указывать на фактическое ядро проекта → «метода нет в версии» будет верно и с учётом правок.
- **Поиск/навигация** (Grep/Serena) — по фактическому ядру; агент увидит реальные, а не эталонные сигнатуры.
- Агент при `core_modified = true` **предупреждает** в ответах, что поведение может отличаться от документации вендора,
  и помечает такие места `[правлено ядро]`.

## Стратегия выхода (техдолг)
Каждую правку ядра оценивай: можно ли заменить на `/local` (копия компонента, обработчик события, наследник класса,
переопределяемый метод)? Что можно — переносить, реестр сокращать. Правка ядра = долг с процентами (боль каждого обновления).

## Чего НЕ делать
- Молча править ядро без патча и записи в реестр.
- Обновлять продукт, не сняв диф (правки исчезнут бесследно).
- Считать, что документация вендора описывает ваше поведение, если ядро правлено — проверяй по коду.
