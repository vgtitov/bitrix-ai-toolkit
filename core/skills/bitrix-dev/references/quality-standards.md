# Стандарты качественного кода Битрикс — читать ПЕРЕД написанием

Смысл: чтобы AI писал корректно **проактивно**, даже когда проверки выключены (режим `off`/`warn`). Это то, что
поймал бы линтер/ревьюер — зашито как знание. Пиши сразу так, а линтеры пусть только подтверждают.

## Структура и организация
- Свой код — в `/local` (компоненты, модули, шаблоны, `php_interface/init.php`), классы — PSR-4 `\Local\...`.
- Ядро `/bitrix/modules` не трогать (перезапишется обновлением). Кастомизация типового компонента — копией в `/local`.
- Бизнес-логику выноси в **сервисы/классы**, а не в `template.php`/`init.php` — так код тестируем и переиспользуем.
- Один класс = одна ответственность; не «God-модуль» в init.php.

## Инфоблоки, каталог, заказы
- Структуру инфоблоков/HL/свойств/прав — **только миграциями** (`sprint.migration`), не руками в БД/админке.
- Товары/цены/остатки часто приходят из 1С (CommerceML), ключ — `XML_ID` (GUID). Не ломай сопоставление.
- Модули: `iblock` (контент/каталог-сущности), `catalog` (цены/склады/SKU), `sale` (корзина/заказ/скидки),
  `highloadblock` (большие справочники). Новый код — D7, где API есть.

## Работа с данными (корректность + производительность)
- **Явный `select`/`filter`** — только нужные поля; фильтр по индексируемым (`IBLOCK_ID`,`ACTIVE`,`SECTION_ID`,`ID`).
- **Никогда — запрос к БД в цикле** (N+1). Собери ID → один запрос `IN(...)`; свойства грузи пакетно.
- D7 ORM (`*Table::getList`) с `cache`/`count_total` предпочтительнее `CIBlockElement::GetList` там, где ORM полна.
- Прямой `$DB->Query` — только для тяжёлых агрегатов/batch, всегда с `$DB->ForSql()`/кастом типов.
- Тяжёлые операции — **кэшируй**: компонент (`startResultCache`), `Data\Cache`/`TaggedCache` (сброс по `iblock_id_*`).
  Ключ кэша включает всё, от чего зависит результат (регион, тип цены, страница, сортировка, права).

## Безопасность (обязательно, до всякого линтера)
- **SQL-инъекции:** ORM или `$DB->ForSql()`/`(int)`. Никогда — конкатенация ввода в запрос.
- **XSS:** пользовательский вывод — `htmlspecialcharsbx()`. Не голый `echo`.
- **Path traversal:** нормализуй/валидируй пути в файловых операциях (`CFile`, `upload/`), не пускай `../`.
- **Права:** `$USER->CanDoOperation()` / проверка доступа перед действием; не доверяй `$_REQUEST`/`$_GET`/`$_POST`.
- **CSRF:** формы с `bitrix_sessid()` + `check_bitrix_sessid()`.
- Секреты/токены — из env, не в коде. Персональные данные клиентов — не в логи и не во внешние сервисы.

## Надёжность: ошибки, транзакции, идемпотентность
- **Исключения, а не «тихие» коды возврата.** Свои доменные исключения (`\Local\Exception\...`), не глушить `@`
  и не ловить `\Throwable` «чтобы не падало». Ловить там, где можешь осмысленно обработать.
- **Транзакции при множественной записи.** Заказ/оплата/списание остатков — атомарно:
  ```php
  $connection = \Bitrix\Main\Application::getConnection();
  $connection->startTransaction();
  try { /* ... */ $connection->commitTransaction(); }
  catch (\Throwable $e) { $connection->rollbackTransaction(); throw $e; }
  ```
  Не оставляй частично применённые изменения.
- **Идемпотентность.** Обработчики событий, агенты, обмен с 1С и вебхуки могут вызваться повторно — операция должна
  быть безопасна при повторе (проверка «уже обработано» по `XML_ID`/внешнему ключу, а не слепое создание дубля).
- **Защита от рекурсии событий:** правка элемента внутри `OnAfterIBlockElementUpdate` снова дёрнет событие — ставь флаг/гард.

## Логирование (framework-native first)
Проверено по официальной документации (`.ai/framework-docs/pages/advanced/logger.md`):
- **Зависимость — от `\Psr\Log\LoggerInterface`** (Битрикс реализует PSR-3: `\Bitrix\Main\Diag\Logger` — базовый класс,
  есть файловый логгер; логгер настраивается, в т.ч. для `AddMessage2Log`).
- В своём коде инъектируй `LoggerInterface` через конструктор, а не зови глобальные функции из бизнес-логики.
- **Monolog** подключать НЕ по умолчанию, а как PSR-3-реализацию **за** `LoggerInterface`, когда нужны sink'и,
  которых нет в ядре (Sentry, ELK, Telegram).
- `[проверить]` В свежих сборках может быть `Diag\LoggerFactory::createById('{module}.{area}.{name}')` (упоминается в
  `bitrix-tools/best-practice`), а `Diag\Logger::create()` — считаться устаревшим. **Сверься с ядром своей версии**
  (`bitrix/modules/main/lib/diag/`) — в текущей официальной документации фигурирует `Diag\Logger::create()`.
- Логируй **события и ошибки**, а не «шум». Уровни: `error` (нужен человек) / `warning` (деградация, ретрай) /
  `info` (бизнес-факт) / `debug` (только стенд). Отладочный вывод не в прод (или под `$USER->IsAdmin()`).
- **Никогда не логируй персональные данные и секреты** (телефоны/почты клиентов, токены, пароли, карты).
  `#[\SensitiveParameter]` (PHP 8.2) маскирует значение в стектрейсе.
- Контекст структурированный: `['orderId' => $id, 'exception' => $e]`, а не конкатенация в строку.

## Штатное ядро вместо сторонних библиотек (официальная линия)
Прежде чем тянуть composer-пакет — проверь, есть ли штатное. Использование стороннего там, где есть ядро, **противоречит
официальным best practices Битрикс** и ломает согласованность (события, права, кэш, обмен).

| Задача | Штатное (дефолт) | Стороннее — только когда |
|---|---|---|
| Логи | `Diag\LoggerFactory` + PSR-3 | нестандартные sink'и (Sentry/ELK) — за `LoggerInterface` |
| HTTP-клиент | **`Main\Web\HttpClient`** (`setTimeout`/`setStreamTimeout`, проверка `=== false` + `getError()` отдельно от `getStatus()`, **`setPrivateIp(false)` против SSRF**) | SDK требует Guzzle или нужны middleware/retry/async — изолировать в интеграционном слое |
| Дата/время | `Main\Type\Date` / `DateTime` (`createFromUserTime`, `toUserTime`) | `\DateTime` — только на границе с внешним API; Carbon — сложные календарные расчёты в своём домене |
| Валидация | **`Main\Validation`** (атрибуты + `ValidationService`) | — |
| Ошибки | `Main\Error` / `ErrorCollection` / `Result`, стабильные строковые коды (`USER_NOT_FOUND`) | — |
| DI | `ServiceLocator` + `.settings.php services` | >40-50 сервисов → внешний контейнер (скомпилированный) |
| Экранирование/санитайз | `htmlspecialcharsbx`, `Main\Text\HtmlFilter`, `Sanitizer` | — |
| Шифрование | `Main\Security\Cipher` | — |
| **Деньги** | ⚠️ **штатного нет** — цены как `float` | **целые копейки** в своём домене или `brick/money`; float даёт расхождения копеек в скидках/налогах |

## Конфигурация вместо хардкода
- **Не хардкодить** ID инфоблоков/свойств/типов цен/складов, пути, URL, e-mail. → в константы/конфиг
  (`config/`, `.settings.php`, свои настройки модуля), а ID инфоблоков — искать по `CODE`/`XML_ID`.
- Секреты и креды — только env/`config/local/.env`, не в коде и не в git.
- Магические числа и строки — именованные константы/enum (PHP 8.1+).

## Переиспользование (DRY, reuse-first)
- Прежде чем писать своё — проверь, есть ли готовое в ядре Битрикс, в `/local`, в marketplace, в composer-пакетах.
- Дублирование логики в двух шаблонах/компонентах — выноси в сервис/хелпер `/local/classes`.
- Не копипастить типовой компонент целиком ради одной правки, если хватает `result_modifier.php`/события.

## Стиль (PSR-12)
- 4 пробела, короткий синтаксис массивов `[]`, один класс на файл, неймспейсы, `use`-импорты без FQN в теле.
- Осмысленные имена; PHPDoc для публичных методов (это же кормит статанализ и IDE).
- Не оставляй `var_dump`/`AddMessage2Log`-мусор в проде; отладку — за `if ($USER->IsAdmin())`.

## Частые ошибки Битрикс-разработчика (AI: проверь себя перед выдачей)
1. Запрос/`GetProperty` в цикле → N+1. → собрать ID, один запрос.
2. Выбор всех `PROPERTY_*` на списке → размножение строк, тяжёлый JOIN. → только нужные.
3. Отключённый кэш компонента (`CACHE_TYPE=N`) на нагруженной странице без причины.
4. Правка в `/bitrix` вместо `/local` → потеря при обновлении.
5. Старое API в новом коде без нужды (`CModule::IncludeModule` → `\Bitrix\Main\Loader::includeModule`).
6. Вывод пользовательских данных без `htmlspecialcharsbx` → XSS.
7. `$DB->Query` с конкатенацией переменной → SQL-инъекция.
8. Тяжёлая логика в `init.php`/`dbconn.php` — выполняется на каждом хите, ломает и композит.
9. Использование метода, которого нет в вашей версии ядра (сверяйся с реальным ядром/справкой).
10. Кэш с приватными данными при общем ключе → утечка между пользователями/регионами.

## Проверка себя без линтера (мини-чек-лист перед выдачей кода)
- [ ] Правки только в `/local`? Структура — миграциями?
- [ ] Нет запроса в цикле? select/filter явные?
- [ ] Тяжёлое закэшировано, ключ полный (регион/цена/страница/права)?
- [ ] Ввод экранирован (SQL/XSS/пути), права проверены, CSRF закрыт?
- [ ] Множественная запись — в транзакции? Операция идемпотентна при повторе?
- [ ] Ошибки — исключениями, не проглочены? Логи без персданных и секретов?
- [ ] Нет хардкода ID/путей/URL — вынесено в конфиг/константы?
- [ ] Не дублирую то, что уже есть (ядро/`/local`/composer)?
- [ ] API есть в нашей версии ядра? Старое/D7 выбрано осознанно?
- [ ] PSR-12, типизация, без отладочного мусора?

> Когда проверки включены (`warn`/`block`) — PHPStan/ast-grep/guard это подтвердят. Но код должен быть верным и БЕЗ них.
