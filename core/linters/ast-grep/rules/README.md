# Правила ast-grep — что здесь и почему не всё

Структурный поиск анти-паттернов по AST (не по тексту). Прогон:
`ast-grep scan -c core/linters/ast-grep/sgconfig.yml <путь>`

## Реализовано (проверено срабатыванием + отсутствием ложных)
| Правило | Ловит |
|---|---|
| `getlist-in-loop` | запрос к БД в цикле (N+1) |
| `getlist-without-limit` | `GetList` без навигации → полный скан таблицы |
| `db-query-concat` | конкатенация переменной в `$DB->Query` → SQL-инъекция (**error**) |
| `cmodule-includemodule` | `CModule::IncludeModule` вместо `Loader::includeModule` |
| `component-cache-off` | `CACHE_TYPE => 'N'` — отключённый кэш компонента |
| `cache-key-literal` | литеральный ключ кэша → утечка между регионами/пользователями |
| `unescaped-echo` | вывод без `htmlspecialcharsbx` → XSS |

## Сознательно НЕ реализовано правилом
**«`startTagCache` без `registerTag`»** — требует анализа потока между операторами, который реляционные
операторы ast-grep (`follows`/`precedes`/`inside`) здесь надёжно не выражают: правило срабатывало и на
корректном коде (проверено на фикстуре с правильным `registerTag`).

**Принцип:** шумное правило хуже отсутствующего. Ложные срабатывания — главная причина, по которой
разработчики отключают линтеры целиком. Поэтому проверка перенесена в слой знаний:
`skills/bitrix-performance/references/caching.md` и чек-лист в `quality-standards.md` — агент проверяет
это чтением кода, а не сопоставлением шаблона.

То же касается любого будущего правила: **сначала фикстура «плохой/хороший», потом правило.**
Если на хорошем коде срабатывает — правило не принимается.
