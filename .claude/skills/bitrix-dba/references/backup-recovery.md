# Резервное копирование и восстановление — MySQL/MariaDB под Битрикс

## Логический vs физический бэкап
- **`mysqldump`** (логический): `--single-transaction` обязателен для InnoDB (снимок без
  блокировки на чтение, консистентный по MVCC) `--routines --triggers --events` если используются.
  Плюс: переносим между версиями/платформами, читаем как SQL. Минус: медленный restore на большой
  базе (последовательное применение INSERT).
- **`mariabackup`/`xtrabackup`** (физический, горячий): копирует файлы данных без остановки
  сервера, восстановление на порядок быстрее на больших базах. Плюс: быстрый RTO. Минус: бинарно
  привязан к похожей версии/архитектуре СУБД.
- Выбор: логический бэкап — ежедневно (небольшая база / нужна переносимость), физический —
  дополнительно на объёмных базах, где восстановление из dump заняло бы часы.

## Регламент (стартовая точка — адаптировать под объём и RPO/RTO проекта)
- Полный бэкап ежедневно (в окно минимальной нагрузки).
- Хранение — согласовано с регламентом ИБ проекта (сколько версий, где — не рядом с продовым
  сервером в единственном экземпляре).
- Синхронизация с файловым бэкапом `/upload` и конфигурацией Битрикс: снимок БД и файлов должен
  быть согласован по времени — иначе после восстановления в БД будут ссылки на файлы, которых нет
  в файловом бэкапе (и наоборот).

## Обязательная проверка восстановимости
**Бэкап без проверенного restore — не бэкап.** Регулярно (не «когда-нибудь понадобится первый
раз») разворачивать дамп/физический бэкап на отдельном стенде и проверять: сервер стартует, число
строк в ключевых таблицах (`b_sale_order`, `b_iblock_element`) соответствует ожиданию, сайт
открывается на восстановленной базе. Без этого шага бэкап — это файл, про который неизвестно,
восстанавливается ли он вообще.

## Согласование с бэкапом самого Битрикс
Модуль «Резервное копирование» Битрикс (`.backup.php`, `/bitrix/admin/backup.php`) снимает и БД, и
файлы вместе — годится для небольших проектов; на объёмных базах предпочтительнее раздельный
бэкап СУБД (mariabackup/mysqldump по расписанию) + файловый бэкап (rsync/снапшот тома) —
согласованные по времени снятия, не через единый php-скрипт, который сам становится узким местом
на большой базе.
