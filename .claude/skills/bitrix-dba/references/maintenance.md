# Регламентное обслуживание MySQL/MariaDB под Битрикс

## OPTIMIZE TABLE
- Точечно на таблицах с высокой долей UPDATE/DELETE: `b_sale_order`, `b_sale_basket`,
  `b_iblock_element` при частом редактировании каталога, `b_catalog_store_product` при активном
  учёте остатков.
- `OPTIMIZE TABLE` на InnoDB технически перестраивает таблицу (эквивалент `ALTER TABLE ...
  ENGINE=InnoDB`); в современных версиях это online DDL с короткими exclusive metadata lock в
  начале/конце операции — не гарантированная блокировка записи на всё время, но поведение зависит
  от версии СУБД и структуры таблицы (внешние ключи, полнотекстовые индексы могут требовать более
  строгого режима) — **проверяй по `[проверить]` для конкретной версии перед прогоном на проде**,
  не считай безопасным по умолчанию, и всё равно планируй в окно минимальной нагрузки на крупной
  таблице (сама перестройка данных — операция не мгновенная, даже если блокировка короткая).
- `information_schema.TABLES` → `DATA_FREE` — оценка фрагментации ДО операции (не точный
  прогноз того, сколько места освободится после OPTIMIZE — реальный результат зависит от версии
  СУБД и данных, сверяй по факту после прогона, не по этому числу заранее).

## ANALYZE TABLE
- После массовых изменений данных (импорт каталога, обмен 1С↔сайт, миграция инфоблока) — обновляет
  статистику, от которой зависит выбор индекса оптимизатором. Дёшево, можно чаще, чем OPTIMIZE.
- Симптом устаревшей статистики: `EXPLAIN` выбирает не тот индекс/полный скан на запросе, который
  раньше отрабатывал быстро, при том же тексте запроса — сначала `ANALYZE`, потом расследование.

## Чистка растущих служебных таблиц
- `b_event_log`, `b_perf_hit`/`b_perf_sql`/прочие `b_perf_*` модуля perfmon, логи агентов —
  накапливаются бесконтрольно на активном сайте.
- Регламент: отдельное периодическое задание (крон/агент Битрикс) с удалением/архивацией старше
  N дней — не ручная разовая операция. Порог N — по регламенту проекта (обычно 30-90 дней для
  perfmon, дольше для event_log при разборе инцидентов).
- Удаление большими партиями (`DELETE ... LIMIT N` в цикле, не один `DELETE` на миллионы строк) —
  иначе долгая блокировка и распухший binlog.

## После обслуживания
Сверить «Панель проверки системы» Битрикс и cache hit ratio (`monitoring-and-locks.md`)
— обслуживание не должно ухудшать показатели; если ухудшило — не та таблица/не то время.
