# Большие каталоги — объёмы, индексы, фасет

Источник: Intervolga «Большие объёмы данных в Битрикс» (habr.com/ru/companies/intervolga/articles/963406/).

## Инфоблоки 2.0
Свойства — колонки таблицы `b_iblock_element_prop_sN` (не строки EAV `b_iblock_element_property`). Применять при **50K+ товаров**.
Ограничение: до 50 свойств на инфоблок. После миграции — **вручную создать индексы MySQL** на связующие колонки:
```sql
CREATE INDEX idx_prop19_elem ON b_iblock_element_prop_s3 (PROPERTY_19, IBLOCK_ELEMENT_ID);
```

## Фасетный индекс (умный фильтр)
Ускоряет фильтрацию по свойствам. Включается только при: фильтр по свойствам + AND + `SECTION_ID` + `ACTIVE='Y'`.
**Деградирует при > 10 млн записей фасета** (тяжёлые JOIN). Объём: `разделы × (товары × свойства) + (SKU × (свойства SKU + типы цен))`.
Тайминги построения: 50K товаров ~50 мин, 100K ~1.5 ч. Свойства настраивать ДО построения (смена состава фильтра = полная перестройка).
Каждый тип цены и множественное свойство SKU удваивают нагрузку; > 10-20 типов цен нецелесообразно.

## Поиск
`b_search_content_stem` на 50K товаров ~29 млн строк, первый поиск 600-1000 SQL / ~8с. Индексировать только нужные поля.

## 1М+ SKU
Свойства → highload-блоки + инфоблоки 2.0. Встроенный поиск/фильтр заменять на **ElasticSearch/OpenSearch/Meilisearch**,
компоненты фильтра перепиливать под внешний движок.

## Highload-блоки
Для больших справочников/характеристик — отдельная таблица + D7 ORM, без оверхеда EAV инфоблоков. На миллионах значений критично.
Минус: тегированный кэш не сбрасывается автоматически — вешать обработчик и чистить вручную.
