# Чужой фреймворк поверх Битрикс — когда «ядро» не только битриксовое

Частая реальность: подрядчик или предыдущая команда вынесли **существенную часть функционала** (нередко 30–40%)
в собственный слой со своим namespace, а API Битрикс там считают устаревшим и почти не используют.

Это **не то же самое**, что правленое ядро (`custom-core.md` — там патчат сам `/bitrix`). Здесь ядро Битрикс целое,
но поверх него живёт **свой фреймворк**, и именно он — источник правды для большей части задач.

## Правило агента: искать в ТРЁХ слоях
```
1. Кастомный слой (namespace подрядчика)  ← часто ГЛАВНЫЙ источник правды
2. Ядро Битрикс (/bitrix/modules)
3. Свой код (/local)
```
**Порядок зависит от `priority` в `config/version-stack.toml`:**
- `over-bitrix` — их методы предпочтительнее: сначала ищи аналог в их слое, битриксовое API — только если у них нет;
- `under-bitrix` — их слой считается legacy, новый код пишем на Битрикс/D7.

Если в конфиге есть `[[custom_layers]]` — **начинай поиск с него**, а не с документации Битрикс.
Документация вендора про их код ничего не знает.

## Как понять чужой фреймворк без документации
Документации у таких слоёв обычно нет. Порядок разведки (дёшево → дорого):
```bash
# 1. Карта слоя: какие классы вообще есть
rg -n "^\s*(final\s+)?(abstract\s+)?class |^\s*interface |^\s*trait " local/vendor-framework --type php | head -50

# 2. Точки входа: что зовут из /local и шаблонов
rg -n "Acme\\\\" local --type php | grep -v "^local/vendor-framework" | head -30

# 3. Как устроен нужный кусок: найти класс и прочитать ЕГО, а не гадать
rg -ln "class ProductRepository" local/vendor-framework
```
Символьно (дешевле по токенам): Serena `find_symbol` / `find_referencing_symbols` по их namespace.

## Что дать инструментам
```neon
# phpstan.neon — кастомный слой ВИДЕН анализатору (сигнатуры оттуда — настоящие)
parameters:
    scanDirectories:
        - local/vendor-framework      # слой подрядчика
        - bitrix/modules/main/lib     # ядро Битрикс
    paths:
        - local/classes               # анализируем СВОЙ код
```
Тогда PHPStan так же честно скажет «у них такого метода нет», как и про ядро Битрикс.

## Правила работы в такой конфигурации
- **Не переписывать их слой на «правильный Битрикс»** без явного решения — это чужой код и чужая зона ответственности.
- **Не спорить с их архитектурой в коде.** Если их подход кажется устаревшим — это тема для обсуждения с людьми,
  а не повод молча переделать.
- **Свои доработки** делаем в `/local`, используя их API так же, как использовали бы битриксовое.
- Сомневаешься, есть ли у них готовое, — **сначала грепни их слой**, потом предлагай своё. Дубли особенно вредны,
  когда код принадлежит другой команде.
- Непроверенное поведение их методов помечай **`[кастомный слой, проверить]`** — там нет ни документации, ни
  гарантий обратной совместимости.

## Если код принадлежит подрядчику (а не вам)
Отдельная реальность: репозиторий и процесс — на стороне подрядчика, вы дорабатываете рядом.
Что toolkit даёт **без всякого участия подрядчика** (не требует от них ничего):
- быстрое **понимание чужого кода** (карта слоя, «где это реализовано», объяснение незнакомого класса);
- **ревью их изменений** — N+1, отсутствие кэша, SQL-инъекции, XSS в их коде вы увидите до прода;
- корректные **свои доработки** поверх их API;
- **локальные проверки только своего кода** (профиль «только изменённое») — их код не трогается вообще.

Командные гейты (PHPStan/CS-Fixer в общем CI) — это уже **политика**, требующая согласия владельца репозитория.
Их можно не внедрять вовсе: пункты выше работают и без этого.
