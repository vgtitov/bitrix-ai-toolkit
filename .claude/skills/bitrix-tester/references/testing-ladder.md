# Лестница проверки — команды, что доказывает и что НЕ доказывает каждая ступень

Правило: бери **самую низкую** ступень, которой хватает для утверждения. Каждая ступень — это
цитируемый артефакт (файл-отчёт/код возврата/HTTP-ответ), не «прогнал и вроде норм».

## Ступень 0 — статика

**Команды:**
```bash
php -l path/to/file.php                                   # синтаксис, секунды
vendor/bin/phpstan analyse --error-format=json             # анти-паттерны, уровни в core/linters/phpstan.neon.dist
ast-grep scan --config core/linters/ast-grep/sgconfig.yml   # N+1, SQL-конкатенация, отключённый кэш, XSS — правила toolkit
vendor/bin/php-cs-fixer fix --dry-run --diff               # стиль (PSR-12) — не блокер по сути, но дешёвая проверка
```
**Доказывает:** нет синтаксических ошибок; код не содержит известных анти-паттернов Битрикс
(запрос в цикле, `GetList` без select, `CACHE_TYPE=>'N'`, конкатенация в `$DB->Query`, echo
пользовательского ввода без экранирования).
**НЕ доказывает:** что страница открывается, что бизнес-логика верна, что заказ оформляется.
**Стоимость:** секунды-минуты, безопасно гонять на каждый коммит.

## Ступень 1 — PHPUnit (юнит)

**Команды:**
```bash
vendor/bin/phpunit --filter TestClassName tests/Unit/TestClassName.php
vendor/bin/phpunit tests/Unit                              # весь модуль
```
**Доказывает:** класс/метод в `/local` (вынесенный в PSR-4, не завязанный на ядро в конструкторе)
делает то, что должен, на явных входах/выходах, включая граничные значения.
**НЕ доказывает:** что код интегрируется с реальным ядром Битрикс (БД, кэш, события) — это по
конструкции юнит-теста, если он мокает зависимости. Если класс тянет ядро Битрикс напрямую
(`CIBlockElement`, `$DB`) — это уже не чистый юнит, см.
`core/skills/bitrix-dev/references/testability.md` про вынос кода в тестируемый вид.
**Стоимость:** секунды-десятки секунд на модуль. PHPUnit — слабое место рынка Битрикс (мало
готовых тестов на легаси) — не жди тестового покрытия там, где его никогда не было; для нового
кода в `/local` — обязательно.

## Ступень 2 — стейджинг-смоук (HTTP/CLI)

**Команды (пример; адаптируй под окружение проекта):**
```bash
curl -sS -w "\n[HTTP %{http_code}]\n" https://staging.example.com/path/to/page/         # тело + код вместе
curl -sS -w "\n[HTTP %{http_code}]\n" https://staging.example.com/local/api/endpoint.php -d 'param=value'
tail -n 50 <путь_error_log_проекта>   # см. references/local/ или .settings.php: exception_handling
```
**Доказывает:** страница/компонент/эндпойнт реально отрабатывает на поднятом окружении (Docker —
`docker/docker-compose.yml` toolkit, или реальный стейджинг), с реальной БД и кэшем, а не только
проходит статику. HTTP 200 + отсутствие новых строк в error_log за время прогона — минимальный
критерий; для сценария с данными — конкретная проверка результата (см.
`staging-verification.md`).
**НЕ доказывает:** что пользователь физически пройдёт сценарий в браузере (JS, вёрстка, формы) и
что производительность приемлема под нагрузкой (`bitrix-performance`).
**Стоимость:** минуты — окружение уже должно быть поднято.

## Ступень 3 — браузерный смоук

**Что делать:** пройти критичный сценарий целиком в браузере на стейджинге — типично «положить
товар в корзину → оформить заказ → увидеть подтверждение», «пройти фильтр каталога», «залогиниться
в личный кабинет». Инструмент — что уже используется в проекте (ручной проход, Selenium/Playwright,
Cypress) — toolkit не навязывает конкретный.
**Доказывает:** пользователь физически увидит и сможет пройти сценарий (вёрстка не сломана, JS не
падает, форма реально отправляется).
**НЕ доказывает:** производительность под нагрузкой, устойчивость к граничным данным вне
пройденного сценария.
**Стоимость:** от минут (ручной проход) до значимого времени на автоматизацию сценария —
затевай автоматизацию только для сценариев, которые будешь гонять регулярно (регресс), не для
разовой проверки.

## Отдельная ось (не следующая ступень) — мутационное тестирование (Infection)

Это НЕ продолжение лестницы 0→3: ступени 0–3 растущей ценой проверяют РАЗНЫЕ свойства
кода/поведения, а мутационное тестирование проверяет КАЧЕСТВО уже существующих PHPUnit-тестов —
вопрос другой оси («тесты реально ловят баги?»), не «выше ли уверенность в коде».
```bash
vendor/bin/infection --filter=path/to/Changed.php --min-msi=<порог>   # только по изменённому файлу/модулю
```
Конфиг — `core/linters/infection.json5` toolkit.
**Доказывает:** существующие PHPUnit-тесты реально ловят баги (мутации кода), а не просто зелёные
из-за слабых assert'ов.
**НЕ доказывает:** ничего про поведение самого кода — не заменяет и не продолжает ступени 0–3.
**Стоимость:** может быть медленной на большом наборе — гоняй точечно на изменённый модуль, не на
весь проект целиком; не имеет смысла без PHPUnit-покрытия (ступень 1) под мутируемым кодом.

## Диагностика «прогон завис / дал ложный результат»

- **PHPUnit висит** — часто тест использует `--bootstrap`, который тянет реальное ядро Битрикс
  (подключение к БД, инициализация `$APPLICATION`) вместо лёгкого bootstrap с моками; проверь, что
  файл, переданный в `--bootstrap` (или заданный в `phpunit.xml`), не инициализирует лишнего для
  конкретного теста.
- **Стейджинг отвечает 200, но страница пустая/старая** — холодный/несброшенный кэш (см.
  `bitrix-performance`), а не баг в коде — сначала сбрось кэш и перепроверь.
- **error_log молчит, но пользователь видит ошибку** — Битрикс подавляет часть warning на проде
  (`display_errors=Off`) — включи `exception_handling.debug` временно на стейджинге, не на проде.
- **PHPStan зелёный, а в проде белый экран** — версия PHP/расширений на стейджинге отличается от
  прода, либо stub-файлы ядра устарели (`core/linters/stubs/`) — сверь версии, не доверяй
  зелёному PHPStan как гарантии рантайма.
