# Варианты работы, Docker и интеграции — что где задействуется

Toolkit собран так, чтобы **работать в любой конфигурации**: от «ничего не установлено, только правила в голове агента»
до «всё в контейнерах + IDE-мост + интеграции». Ничего из перечисленного не обязательно.

---

## 1. Четыре варианта работы

| Вариант | Что нужно | Что получаешь | Кому |
|---|---|---|---|
| **A. Только знания** (нулевой порог) | ничего ставить не надо | Агент читает `AGENTS.md` + скиллы и пишет по стандартам Битрикс: `/local`-гейт, два ядра, кэш, N+1, безопасность. Проверок нет | попробовать за 5 минут; правки в чужом проекте, куда нельзя ставить инструменты |
| **B. Локальные проверки** (рекомендуемый) | PHP + Composer + линтеры локально (`onboard/install.sh`) | То же + PHPStan/CS-Fixer/ast-grep/N+1-guard, git-хуки, LSP | основная разработка на своей машине |
| **C. Проверки в Docker** | Docker | То же, что B, **без установки PHP и линтеров локально**; одинаковые версии у всех и в CI | кто не хочет ставить PHP; единая версия инструментов; CI |
| **D. Полный контур** | B/C + MCP + IDE-мост + интеграции | + поиск по официальной документации, символьная навигация (Serena/LSP), диагностики PhpStorm, Jira/Confluence | максимальная отдача |

Варианты **комбинируются**: например, знания + Docker-проверки, без локального PHP.

---

## 2. Что вынесено в Docker (и что принципиально НЕ вынесено)

### ✅ Вынесено — `docker/`
**Воспроизводимая среда проверок кода.** Образ (`docker/Dockerfile`) содержит:
- PHP 8.3 CLI + Composer;
- линтеры: **PHPStan** (+deprecation-rules, +strict-rules), **PHP-CS-Fixer**, **PHP_CodeSniffer**, **Rector**;
- **ast-grep** (структурные анти-паттерны);
- сам toolkit: `core/` (правила, ast-grep-правила, линтер-конфиги), `scripts/` (N+1-guard, checks_config), `tests/`;
- `entrypoint` с командами: `check` (всё), `guard`, `astgrep`, `phpstan`, `selftest`, `sh`.

Проект монтируется в `/work`, конфиг опциональности — томом. **Режим проверок (`off/warn/block`) уважается внутри контейнера.**

```bash
docker compose -f docker/docker-compose.yml run --rm checks              # весь проект
docker compose -f docker/docker-compose.yml run --rm checks check local/ # только свой путь
BITRIX_AI_CHECKS=block docker compose -f docker/docker-compose.yml run --rm checks
docker compose -f docker/docker-compose.yml run --rm checks selftest     # самотест toolkit
```

### ❌ НЕ вынесено (и почему)
| Компонент | Почему остаётся локальным |
|---|---|
| **AI-агент** (Claude Code/Cursor/…) | работает на машине разработчика, у него свой рантайм и авторизация |
| **Language Server** (Intelephense/Phpactor) | LSP привязан к рабочему пространству разработчика (per-project индекс), в общем контейнере смысла нет |
| **Serena / MCP-навигация** | то же: индексирует локальный проект |
| **git-хуки** | срабатывают в локальном репозитории на коммите |
| **IDE-мост** (JetBrains MCP) | требует запущенной IDE с открытым проектом |
| **Сам Битрикс-сайт** | toolkit не поднимает сайт; для проверки кода запущенный сайт не нужен. Окружение сайта — BitrixVM/bitrixdock (см. `bitrix-admin-devops`) |

**Принцип:** в контейнер вынесено то, что **не привязано к рабочему месту** — статические проверки. Всё, что требует
контекста разработчика (агент, LSP, IDE, хуки), остаётся локальным.

### Актуализация данных в Docker
Образ содержит версии линтеров на момент сборки → **пересобирай образ**, чтобы обновить:
```bash
docker compose -f docker/docker-compose.yml build --pull --no-cache checks
```
Официальная документация Битрикс (`.ai/framework-docs`) обновляется **отдельно и локально**
(`sh scripts/fetch_official_docs.sh`) — она нужна агенту, а не контейнеру проверок, и в образ не зашивается,
чтобы не устаревала вместе с ним.

## 3. Интеграции с инструментами — все опциональны

| Интеграция | Как подключается | Что даёт | Без неё |
|---|---|---|---|
| **PHPStan** (+deprecation) | composer в проекте / Docker | типы, баги, **устаревшее API**, «метода нет в этой версии ядра» | агент пишет по знаниям скилла |
| **PHP-CS-Fixer / PHPCS** | composer / Docker | PSR-12, авто-формат | стиль по правилам скилла |
| **Rector** | composer / Docker | апгрейд синтаксиса PHP под таргет | ручной апгрейд |
| **ast-grep** | brew/npm / Docker | структурные анти-паттерны (SQL-инъекции, старое API, кэш) | остаётся pure-Python N+1-guard |
| **N+1 guard** | входит в toolkit (Python stdlib) | запрос в цикле на коммите | — |
| **deptrac** | composer (опц.) | контроль слоёв: домен не знает про `Bitrix\` | правило «на честном слове» |
| **phpstan-disallowed-calls** | composer (опц.) | запрет `CModule::IncludeModule`, `var_dump`, `curl_exec`… | правила в скилле |
| **composer audit / roave/security-advisories** | composer (опц.) | уязвимые зависимости | — |
| **MCP `bitrix-docs`** | `claude mcp add --transport http …` | официальная справка REST | поиск по локальной доке |
| **Официальная документация локально** | `sh scripts/fetch_official_docs.sh` | агент грепает первоисточник вместо памяти | ответы по памяти → риск ошибок |
| **Serena (MCP)** | `claude mcp add serena …` | символьная навигация + диагностики | Grep/ripgrep |
| **php-lsp (MCP)** | `mcp-language-server` + Intelephense | LSP агенту: go-to-def, hover, диагностики | Grep + линтеры |
| **JetBrains MCP** | PhpStorm 2025.2+ → Settings → Tools | инспекции/рефакторинги IDE агенту | автономный режим |
| **Jira / Confluence** | `config/local/.env` + `scripts/atlassian.py` | ЧТЗ и база знаний одной командой | ручной перенос контекста |
| **Zabbix / Prometheus** | env (опц.) | метрики для диагностики производительности | штатный perfmon Битрикс |

**Правило graceful degradation:** любой отсутствующий инструмент → шаг **тихо пропускается**. Ничего не падает,
работа не блокируется. Проверено онбордингом на машине без ast-grep.

## 4. Опциональность проверок — три режима

| Режим | Проверка | Поведение агента | Коммит |
|---|---|---|---|
| **`off`** | не запускается | пишет по знаниям скилла | проходит |
| **`warn`** ⭐дефолт | запускается | **сообщает** о проблемах, предлагает фикс | **проходит** |
| **`block`** | запускается | **обязан починить** до завершения | останавливается при находках |

Источники (по приоритету): `env BITRIX_AI_CHECKS` → `config/local/checks.toml` → `config/checks.toml` → дефолт `warn`.
Точечно по каждой проверке — секции `[checks.<имя>]`; ограничение своими путями — `[scope].paths`.

```bash
python3 scripts/checks_config.py n1_guard   # какой режим действует сейчас
BITRIX_AI_CHECKS=off  …                     # разово выключить всё
```

**Ключевое:** качество кода **не зависит от режима** — стандарты зашиты в скилл
(`bitrix-dev/references/quality-standards.md`). Проверки лишь подтверждают, а не заменяют знание.

## 5. Индивидуально vs командой

- **Индивидуально:** клонировал → `onboard/install.sh` → работаешь. Настройки в `config/*.toml`, режим `warn`.
- **Командой/компанией:** общий слой настроек (`config/local/`) выносится в **отдельный приватный репозиторий**
  и подключается клоном/симлинком — см. `docs/LOCALIZATION.md`. Ядро toolkit остаётся обезличенным и обновляется
  независимо. Единая версия инструментов у всех — через Docker-образ (вариант C).
- **Никто никому ничего не навязывает:** каждый выбирает режим проверок под себя и свои пути.
