# Совместимость версий PHP ↔ 1С-Битрикс и проверка корректности кода по версии

Цель: писать и проверять код **под конкретную версию** — не предлагать API, которого нет в твоём ядре, не использовать
устаревшее там, где есть замена, и наоборот — использовать legacy-API там, где D7-обёртки ещё нет (иначе не заработает).

## 1. Матрица PHP ↔ Битрикс (ориентир)

| Версия PHP | Статус для BUS | Комментарий |
|---|---|---|
| **8.3** | ✅ рекомендуется | Целевая для нового кода. Rector/PHPStan таргетируй сюда. |
| **8.2** | ✅ минимум поддержки | С 01.02.2026 обновления продукта **недоступны** на PHP < 8.2. |
| 8.1 | ⚠️ устаревает | Объявлен устаревшим; апгрейд через Rector. |
| 7.4 / 8.0 | ❌ вне поддержки | Массовый legacy; цель — миграция на 8.2/8.3. |

Фиксируй фактические версии проекта в `config/version-stack.toml` (`[php].version`, `[bitrix].main_version`, `[modules].*`).
Принцип: **справку и синтаксис бери по своей версии; не предлагай новее того, что доступно.**

## 2. Два ядра — что использовать в новом коде, а что вынужденно legacy

- **Новый код — D7** (`Bitrix\Main\*`, `*Table::getList()`, `Loader::includeModule()`, `EventManager`).
- **Вынужденно старое ядро** — там, где D7-обёрток НЕТ (иначе не заработает): значительная часть `sale` (оформление
  заказа, скидки, правила корзины), часть `catalog` (операции с ценами/складами). Список для твоего проекта фиксируй
  в `config/version-stack.toml` → `[conventions].legacy_required`, чтобы линтер/агент НЕ «исправлял» это на D7.

## 3. Механизм проверки корректности по версии (зашит в toolkit)

Готового «BSL-LS для Битрикс» нет — собран из готовых частей. Работает так:

### 3.1. «Метода нет в этой версии» — через реальное ядро
PHPStan видит символы из того ядра, которое ты дал ему в `scanDirectories`. Клади **распакованное ядро СВОЕЙ версии**
(из `bitrix-toolkit/bitrix-ci`, `bitrix-tools/env-docker` или бэкапа) → PHPStan сам выдаёт `Call to an undefined method`,
если метода в этой версии нет. Это и есть «режим совместимости по версии». Настроено в `core/linters/phpstan.neon.dist`
(`scanDirectories`).

### 3.2. «Метод устаревший» — автоматически, без своих списков
Ядро Битрикс **само размечено `@deprecated`** в PHPDoc. Подключаешь `phpstan/phpstan-deprecation-rules` (уже в
`phpstan.neon.dist` через `includes`) → PHPStan выдаёт «используется устаревший метод ядра». Список вести не нужно —
он живёт в аннотациях вендора и обновляется с версией ядра.

### 3.3. Корректный анализ ORM — через `orm annotate`
Встроенная CLI ядра генерирует PHPDoc-аннотации ORM-сущностей под ТВОЮ версию:
```bash
php bitrix/modules/main/cli.php orm annotate    # (путь CLI зависит от версии; см. bitrix/modules/main/lib/cli)
```
Результат (`orm_annotations.php`) подключается в `phpstan.neon.dist` (`scanFiles`) → корректные типы `getList/add/update`.

### 3.4. Апгрейд синтаксиса под версию PHP — Rector
`core/linters/rector.php` таргетирован на PHP-версию из version-stack (`UP_TO_PHP_83`). Всегда `--dry-run` → apply.
Rector НЕ мигрирует «старое ядро → D7» (семантика разная, риск) — только синтаксис PHP.

### 3.5. Анти-паттерны специфики Битрикс — ast-grep/guard
`core/linters/ast-grep/rules/` ловит `CModule::IncludeModule` (→ `Loader::includeModule`), N+1, SQL-инъекции, XSS,
отключённый кэш. Плюс pre-commit `bitrix_guard.py` (N+1). См. `core/linters/`.

## 4. Итоговый порядок настройки проверок под версию
1. Заполни `config/version-stack.toml` (PHP, версии модулей, legacy_required).
2. Положи ядро своей версии по `[bitrix].core_path`; пропиши в `phpstan.neon` `scanDirectories`.
3. Сгенерируй `orm_annotations.php` (`orm annotate`) → `scanFiles`.
4. Rector `UP_TO_PHP_8x` под свою PHP-версию.
5. Хуки/CI: PHPStan (+deprecation) + ast-grep + php-cs-fixer прогоняются автоматически.
