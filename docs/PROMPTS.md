# Готовые запросы — что говорить агенту

Сложные промпты не нужны: правила уже в `AGENTS.md` и скиллах, агент их подхватывает сам. Но с чего-то надо начать —
ниже рабочие формулировки под типовые задачи Битрикс-разработчика. Копируйте и правьте под себя.

---

## Разведка в незнакомом проекте
```
Составь карту проекта: какие модули ядра используются, что лежит в /local,
есть ли кастомный слой со своим namespace. Коротко, без воды.
```
```
Где в проекте реализована <функция: расчёт скидки / выгрузка в 1С / умный фильтр>?
Ищи в кастомном слое, в ядре и в /local. Покажи файлы и точки входа.
```
```
Объясни, что делает <файл/класс> и как он вписан в архитектуру. Построчно по ключевым местам.
```

## Разбор чужого/старого кода
```
Прочитай <файл> и объясни: что он делает, какие есть проблемы (производительность, безопасность,
корректность), что бы ты изменил в первую очередь. Не правь пока — только разбор.
```
```
Этот код писали не мы. Найди в нём места, которые сломаются при обновлении Битрикс
или при росте объёмов каталога.
```

## Написание кода
```
Нужно <задача>. Сначала покажи, где это лучше сделать (точка расширения: result_modifier,
событие, свой компонент, модуль) и почему — потом пиши код.
```
```
Реализуй <задача>. Правки только в /local. Структуру инфоблоков не трогай — если нужна,
подготовь миграцию sprint.migration. Покажи diff перед применением.
```
```
Проверь по нашему ядру, есть ли метод <метод> в нашей версии и не устарел ли он.
Если нет — предложи актуальный аналог.
```

## Производительность
```
Найди в <каталог> места, где запрос к БД идёт в цикле (N+1). Покажи файл:строку
и как переделать пакетно.
```
```
Страница <URL/компонент> медленная. Разбери по порядку: кэш компонента, выборки,
лишние свойства, тяжёлый init.php. Что чинить первым по эффекту?
```
```
Проверь этот компонент: правильно ли настроен кэш, входят ли в ключ кэша регион и тип цены,
не утечёт ли персональное между пользователями.
```

## Ревью
```
Отревьюй мои изменения (git diff) по чек-листу: N+1, кэш, безопасность (SQL/XSS/права/CSRF),
транзакции и идемпотентность, хардкод ID, соответствие версии ядра. Кратко и по делу.
```
```
Отревьюй этот PR подрядчика. Меня интересуют только реальные риски: производительность
на объёмах и безопасность. Стиль не трогай.
```

## Тесты и рефакторинг
```
Напиши PHPUnit-тесты на <класс>. Сначала характеризационные — зафиксируй ТЕКУЩЕЕ поведение,
включая странное, чтобы поймать регресс при рефакторинге.
```
```
Этот класс разросся. Предложи, как разрезать по сценариям (не по слоям), и покажи
первый безопасный шаг отдельным коммитом.
```

## Обновление и совместимость
```
Мы поднимаем PHP до 8.3. Прогони Rector в режиме --dry-run по /local/classes
и покажи, что он собирается изменить. Ничего не применяй.
```
```
Найди в нашем коде использование устаревшего API ядра. Для каждого — актуальная замена.
```

## Приёмы, которые реально помогают

**Просите план до кода.** «Сначала покажи, где и почему, потом пиши» — ловит неверную точку расширения до того,
как написан код.

**Просите diff, а не «сделай».** Видите, что меняется, до применения.

**Говорите про ограничения.** «Не трогай структуру БД», «только /local», «стиль не трогай» — агент их соблюдает.

**Просите пометить непроверенное.** Правило `[проверить]` уже зашито: агент помечает то, что не подтвердил кодом
или документацией. Если пометки нет — значит, проверил.

**Не пересказывайте код в запросе.** Он его прочитает сам — просто назовите файл. Пересказ тратит контекст и вносит
искажения.

**Дисциплина для крупной задачи** (если хочется структуры):
```
Проанализируй задачу → спланируй → покажи план → выполни → прогони проверки → покажи что сделал.
```
