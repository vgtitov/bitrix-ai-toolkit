# Зачем стабы и инструменты — простым языком

Документ для тех, кто впервые видит этот набор и справедливо спрашивает: «зачем нам ещё одна система, которую надо
поддерживать?». Ниже — что каждый инструмент делает, **какую конкретную боль снимает**, и где реальная сложность,
а где её нет.

---

## 1. Стабы: главный источник недопонимания

### Проблема
В репозитории Битрикс-проекта обычно лежит **только `/local`**. Ядро (`/bitrix/modules`) в git не хранят — оно
приходит с дистрибутивом и перезаписывается при обновлении. Итог: и IDE, и статический анализатор, и AI-агент
**не видят классов ядра**.

Практически это выглядит так:
```php
$el = CIBlockElement::GetList([], ['IBLOCK_ID' => 5]);
//    ^^^^^^^^^^^^^^ "Undefined class CIBlockElement"
```
- PhpStorm не подсказывает методы и параметры;
- PHPStan сыпет сотнями ложных «класс не найден» — анализ бесполезен;
- **AI-агент вынужден угадывать сигнатуры** → отсюда и берутся «галлюцинации про Битрикс».

### Что такое стабы
**Стабы (stubs, «заглушки») — это объявления классов и методов ядра без тел.** Только сигнатуры и PHPDoc:
```php
class CIBlockElement {
    /** @return CDBResult */
    public static function GetList($arOrder = [], $arFilter = [], $arGroupBy = false,
                                   $arNavStartParams = false, $arSelectFields = []) {}
}
```
Инструменты читают их и понимают: класс существует, у метода такие параметры и такой возврат. Код при этом
**не исполняется** — стабы нужны только для анализа.

### Два способа (нужен один)
| Способ | Что это | Плюс | Минус |
|---|---|---|---|
| **Реальное ядро рядом** (`bitrix-toolkit/bitrix-ci` в `vendor`, либо просто путь к ядру проекта) | настоящий код ядра | **точно ваша версия**: анализатор сам скажет «этого метода нет в вашей версии» | объём; репозиторий пакета архивный (проверить под PHP 8.3) |
| **Стабы** (`matiaspub/bxApiDocs`) | только сигнатуры | лёгкие, быстрые | не привязаны к вашей версии, есть пробелы |

**Рекомендация:** указать анализатору путь к **фактическому ядру проекта** (`scanDirectories` в `phpstan.neon`) —
оно и так лежит на диске, просто не в git. Стабы — дополнение для IDE.

### Сложность — есть ли она?
**Практически нет.** Это 2–3 строки в конфиге:
```neon
parameters:
    scanDirectories:
        - bitrix/modules      # ядро НЕ анализируем, но даём «увидеть»
    excludePaths:
        - '*/bitrix/*'
```
Никакой новой системы не появляется, ничего не надо поддерживать: ядро уже на диске, мы лишь показываем на него пальцем.

**Реальные (небольшие) нюансы, о которых честно стоит знать:**
1. Ядро большое → первый прогон анализатора и индексация IDE идут дольше. Лечится ограничением списка модулей
   (`main`, `iblock`, `catalog`, `sale`, `highloadblock` — обычно достаточно).
2. `bitrix-ci` архивный (окт. 2024) — под PHP 8.3 может потребовать проверки. Поэтому путь к реальному ядру надёжнее.
3. Ядро **не коммитим** в git (оно в `.gitignore`) — стабы/путь настраиваются локально и в CI-образе.

## 2. Остальные инструменты — что делает каждый

| Инструмент | Что делает | Какую боль снимает | Сложность |
|---|---|---|---|
| **PHPStan** | статический анализ: типы, несуществующие методы, мёртвый код. С флагом deprecation — ловит **устаревшее API ядра** (ядро само размечено `@deprecated`) | «метода нет в нашей версии», «используем устаревшее», опечатки — до запуска | конфиг-файл; уровень строгости настраивается (легаси — низкий, новый код — выше) |
| **PHP-CS-Fixer** | приводит стиль к PSR-12 **автоматически** | споры о форматировании в ревью | ноль: правит сам |
| **ast-grep** | поиск по структуре кода (не по тексту): «запрос внутри цикла», «конкатенация в SQL» | ловит анти-паттерны, которые regexp не найдёт | правила уже написаны в toolkit |
| **N+1 guard** | скрипт на Python: находит запрос к БД в цикле среди изменённых файлов | классическая причина «сайт лёг» — **до** прода | ноль зависимостей (stdlib) |
| **Rector** | автоматически переписывает синтаксис под новую версию PHP | апгрейд 7.4 → 8.2/8.3 без ручной вычитки | всегда сначала `--dry-run` |
| **deptrac** | проверяет, что слои не лезут друг в друга (домен не знает про `Bitrix\`) | «через год всё связано со всем» | опционален; нужен, когда есть слои |
| **Language Server** (Intelephense/Phpactor) | то, что даёт PhpStorm: go-to-definition, hover, автодополнение — но **агенту** | агент перестаёт гадать, видит реальные сигнатуры | `npm i -g intelephense` |
| **MCP** | канал, по которому агент ходит в инструменты (справка, поиск по коду, диагностики IDE) | агент отвечает по документации, а не по памяти | одна команда `mcp add` |

## 3. Частые возражения — и что на них ответить

**«Это ещё одна система, которую надо поддерживать»**
Нет. Это **конфиг-файлы в вашем же репозитории** и обычные composer-пакеты в `require-dev`. Ничего не деплоится
на прод, ничего не крутится фоном. Убрать = удалить пару файлов.

**«Линтеры будут блокировать работу»**
По умолчанию **не блокируют**. Режим `warn`: показал проблему — и пропустил. Строгий режим (`block`) включается
осознанно и **каждым для себя**, на своих путях. Есть глобальный выключатель `BITRIX_AI_CHECKS=off`.

**«У нас легаси, PHPStan захлебнётся»**
Для этого есть два бюджета: легаси — низкий уровень (1) или baseline (замораживает существующие ошибки), новый код
в `/local/classes` — уровень 6+. Никто не требует чинить 10 лет истории.

**«Придётся менять IDE»**
Нет. Агент живёт в терминале. PhpStorm остаётся PhpStorm (и даже усиливается — через MCP агент видит его инспекции).
VS Code, Cursor, vim — тоже работают. Один контур, разные входы.

**«AI будет писать за нас код и наделает ерунды»**
Смысл контура ровно обратный: **ограничить** агента. Он обязан проверять API по реальному коду ядра, соблюдать
`/local`-гейт, прогонять линтеры, а непроверенное помечать `[проверить]`. Правку принимает человек.

**«Нам это не нужно, мы и так знаем Битрикс»**
Инструменты нужны не вместо знания, а чтобы: (1) не держать в голове, какие методы есть в **вашей** версии ядра;
(2) ловить N+1 и дырки до прода; (3) новичок входил в проект за вечер, а не за месяц; (4) AI не выдумывал.

**«Стабы — это костыль»**
Это стандартная практика всей PHP-экосистемы (у WordPress, Magento — то же самое). У Битрикс просто нет
официальных стабов, поэтому их роль выполняет реальное ядро проекта.

## 4. Минимальный вход (если всё кажется избыточным)

Можно начать с **нуля установок**: агент читает `AGENTS.md` и скиллы и уже пишет по стандартам Битрикс —
`/local`-гейт, кэш, отсутствие N+1, безопасность. Проверок нет, ничего не ставится.

Дальше — по одному шагу, в любом порядке:
1. путь к ядру в `phpstan.neon` (стабы) → анализ перестаёт быть слепым;
2. `php-cs-fixer` → стиль сам;
3. N+1-guard в хуке (режим `warn`) → предупреждает, не мешает;
4. остальное — по вкусу.

**Каждый шаг самостоятелен и обратим.** Ничего не ломается, если остановиться на любом.
