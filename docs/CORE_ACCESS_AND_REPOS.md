# Доступ к ядру Битрикс и организация репозиториев

Два связанных вопроса: **чем «кормить» анализатор и AI-агента** (реальное ядро vs стабы) и **как устроить
репозитории и процесс разработки**, чтобы это работало у одного человека, у команды и в CI.

---

## Часть 1. Лестница решений: чем дать агенту «увидеть» ядро

Поднимайся по ступеням, пока не закроешь свою потребность. Выше ступень — точнее анализ, но дороже поддержка.

### Ступень 0 — ничего (по умолчанию, если не настроить)
Агент и PHPStan не видят классов ядра.
**Следствие:** галлюцинации сигнатур, сотни ложных «класс не найден», статанализ бесполезен.
👉 Приемлемо только для варианта «агент пишет по правилам скилла, проверок нет».

### Ступень 1 — стабы (`matiaspub/bxApiDocs`)
Только сигнатуры без тел.
- ➕ лёгкие (мегабайты), быстрая индексация, спокойно живут в composer.
- ➖ **не привязаны к вашей версии** → не поймают «этого метода нет в вашем ядре»;
- ➖ есть пробелы (спарсены с документации, не из кода); проект **архивирован с 2022**.
👉 Годится, когда ядра под рукой нет (правка в чужом окружении, ноутбук без дистрибутива).

### Ступень 2 — **реальное ядро проекта на диске (рекомендуемый дефолт)** ⭐
Ядро уже лежит рядом (`bitrix/modules`) — просто показываем на него анализатору, **не коммитя в git**.
```neon
# phpstan.neon
parameters:
    scanDirectories:            # видит, но НЕ анализирует
        - bitrix/modules/main/lib
        - bitrix/modules/iblock/lib
        - bitrix/modules/catalog/lib
        - bitrix/modules/sale/lib
        - bitrix/modules/highloadblock/lib
    excludePaths: ['*/bitrix/*']
```
```toml
# config/version-stack.toml
[bitrix]
core_path = "bitrix/modules"
```
- ➕ **точно ваша версия** → PHPStan сам скажет «метода нет», а `phpstan-deprecation-rules` поймает устаревшее
  (ядро размечено `@deprecated`);
- ➕ ноль дополнительной инфраструктуры: ядро и так на диске;
- ➕ учитывает **правки ядра**, если они есть (`core_modified = true`);
- ➖ у каждого разработчика своя копия → возможен дрейф версий;
- ➖ в CI ядра нет (см. ступени 3–4).
👉 **Это дефолт для локальной разработки.**

### Ступень 3 — ядро как composer-пакет (`bitrix-toolkit/bitrix-ci` или свой)
Минимальная сборка ядра приезжает в `vendor/` по `composer install`.
- ➕ **воспроизводимо**: одинаково у всех и в CI, версия зафиксирована в `composer.lock`;
- ➕ IDE и PHPStan видят классы автоматически;
- ➖ публичный `bitrix-ci` архивный (окт. 2024) и покрывает не все модули → под PHP 8.3 проверять;
- ➖ свой пакет = своя инфраструктура (приватный Packagist/Satis).
👉 Когда нужен **CI** и единообразие версий.

### Ступень 4 — ядро в приватном git-репозитории (зеркало по версиям)
Отдельный приватный репо `bitrix-core-mirror` с тегами по версиям (`v24.100.0`, …), подключается сабмодулем
или клонируется в CI.
- ➕ строгий контроль версии; удобно диффать ядро и вести патчи (если ядро правлено);
- ➕ CI берёт ровно ту версию, что на проде;
- ➖ вес и обслуживание; нужен процесс обновления при апдейте продукта.
👉 Когда **несколько проектов/стендов** и важна воспроизводимость + учёт правок ядра.

### Ступень 5 — ядро внутри Docker-образа (приватный registry)
Образ для проверок с уже распакованным ядром нужной версии.
- ➕ CI стартует мгновенно, ничего не клонирует;
- ➖ образ надо пересобирать при обновлении ядра; хранить только в **приватном** registry.
👉 Для зрелого CI с большим числом прогонов.

### ⚠️ Юридическая рамка (важно)
Ядро «1С-Битрикс: Управление сайтом» — **проприетарный код по лицензии**.
- ❌ **Никогда не публиковать ядро в публичном репозитории.**
- ⚠️ Приватный репозиторий / приватный registry — **сверьтесь с условиями своей лицензии** перед тем, как
  класть туда ядро. `[проверить у себя]`
- ✅ Ядро **на диске разработчика и на сервере** — это штатное использование продукта, вопросов не вызывает.
- ✅ Публичным в нашем toolkit является **только конфиг** (`scanDirectories` с путём), но не сам код ядра.
  Поэтому `.gitignore` содержит `/bitrix` — это не только про вес, но и про лицензию.

### Итоговая рекомендация
| Ситуация | Ступень |
|---|---|
| Один разработчик, локально | **2** (реальное ядро на диске) |
| Команда без CI | **2** + фиксация версии в `version-stack.toml`, чтобы ловить дрейф |
| Команда с CI | **2** локально + **3 или 4** в CI |
| Ядро правлено | **2** (обязательно фактическое) + патчи в git, `core_modified = true` |
| Нет доступа к ядру (чужое окружение) | **1** (стабы) как временная мера |

**Стабы vs реальное ядро:** реальное ядро лучше почти всегда — оно точное и версионное. Стабы остаются как
запасной вариант и как ускорение индексации IDE, если ядро слишком тяжёлое.

## Часть 2. Архитектура репозиториев

### Вариант A — один репозиторий проекта (рекомендуемый старт) ⭐
```
project-repo/                     # git
├── local/                        # ВЕСЬ наш код
│   ├── classes/                  # PSR-4 \Local\  (домен, сервисы, репозитории)
│   ├── components/ templates/ modules/
│   └── php_interface/init.php
├── migrations/                   # sprint.migration (структура)
├── patches/core/                 # ТОЛЬКО если ядро правлено: .patch + REGISTRY.md
├── composer.json  phpstan.neon  rector.php  .php-cs-fixer.dist.php
├── config/                       # version-stack.toml, checks.toml (личное — в .gitignore)
└── .gitignore                    # /bitrix, /upload, /vendor, .ai/
                                  #   ↑ ядро НЕ в git: лицензия + вес
```
Ядро приезжает из дистрибутива/бэкапа и лежит рядом; `phpstan.neon` смотрит на него через `scanDirectories`.
- ➕ просто, один клон, понятный ревью;
- ➖ в CI ядра нет → либо ступень 3/4, либо в CI гонять только те проверки, которым ядро не нужно
  (ast-grep, N+1-guard, cs-fixer, PHPStan level 1 по своему коду).

### Вариант B — проект + приватное зеркало ядра
```
project-repo/            ← код проекта (как в A)
bitrix-core-mirror/      ← ПРИВАТНЫЙ: ядро с тегами по версиям
   tags: v24.100.0, v24.200.0 …
```
CI: `git clone --depth 1 -b v24.200.0 <core-mirror>` → `scanDirectories` на него.
- ➕ воспроизводимость и точная версия в CI; удобно диффать при обновлении продукта;
- ➖ обслуживание зеркала; ⚠️ проверить лицензию.

### Вариант C — ядро composer-пакетом
`composer require --dev company/bitrix-core:24.200.*` из приватного Satis/Packagist.
- ➕ версия в `composer.lock`, одинаково локально и в CI;
- ➖ нужен приватный репозиторий пакетов.

### Вариант D — монорепо нескольких сайтов
```
monorepo/
├── sites/shop/local/…
├── sites/corp/local/…
├── packages/shared-domain/      # общий код как composer-пакет по path-репозиторию
└── tools/                       # общие phpstan.neon, ruleset, CI
```
- ➕ переиспользование общего домена, единые правила;
- ➖ тяжёлый CI, нужна дисциплина границ (здесь **deptrac** особенно полезен).

### Где живёт слой настроек организации
```
bitrix-ai-toolkit/               # публичный, обезличенный (этот репозиторий)
bitrix-ai-toolkit-<company>/     # ПРИВАТНЫЙ: checks.toml, version-stack.toml, конвенции, .env
    ↓ подключается
project-repo/config/local/       # клон или симлинк (в .gitignore)
```
Без приватного слоя всё работает на дефолтах — см. `docs/LOCALIZATION.md`.

## Часть 3. Процесс разработки

### Откуда берётся ядро в каждой среде
| Среда | Источник ядра | Зачем |
|---|---|---|
| Машина разработчика | дистрибутив/бэкап, лежит рядом (не в git) | IDE + PHPStan + агент видят реальные сигнатуры |
| CI | ступень 3/4/5 (composer-пакет, зеркало или образ) | воспроизводимый анализ |
| Стейдж/прод | штатная установка продукта | работа сайта |

### Цикл задачи
```
1. Анализ        → скилл bitrix-analyst: impact-чеклист, выбор точки расширения, при необходимости ADR
2. Ветка         → feature/<задача>
3. Код           → только /local; структура — миграциями; агент сверяется с ядром и офиц. документацией
4. Локальные     → хук после правки: php-cs-fixer + PHPStan (режим warn — не мешает)
   проверки        плюс по желанию: ast-grep, deptrac, N+1-guard на коммите
5. PR/ревью      → CI: cs-fixer --dry-run, PHPStan, ast-grep, N+1-guard, тесты
6. Мерж          → main
7. Деплой        → выкладка /local (rsync/Deployer) + `php sprint.php migrate` + сброс кэша
8. Проверка      → perfmon/логи; при регрессе — откат релиза и `migrate down`
```

### Что гонять в CI, если ядра там нет (частый случай)
Работает **без** ядра: `php -l`, ast-grep-правила, N+1-guard, PHP-CS-Fixer, PHPUnit-юниты домена (он же не зависит
от Битрикс — в этом и смысл ACL), `composer audit`, deptrac.
Требует ядра: PHPStan выше level 1 по коду, который трогает ядро.
👉 Практичный компромисс: **в CI без ядра — всё кроме глубокого PHPStan; глубокий PHPStan — локально или
в CI со ступенью 3/4.**

### Обновление продукта (когда ядро меняется)
1. Снять диф с эталоном (если ядро правлено): `diff -ru vanilla/modules project/bitrix/modules > core-diff.txt`.
2. Обновить продукт на стейдже.
3. Переприменить патчи из `patches/core/`, обновить `REGISTRY.md`.
4. Обновить `version-stack.toml` (версии модулей) и зеркало/пакет ядра (ступень 3/4).
5. Прогнать PHPStan — **deprecation-rules покажут, что устарело в новой версии**.
6. Прогнать тесты, затем прод.

## Часть 4. Если «идеальный» вариант не подходит

Инструмент не должен диктовать процесс. Реальные ограничения и рабочие компромиссы:

| Ограничение | Компромисс |
|---|---|
| Нельзя класть ядро никуда, кроме машины | Ступень 2 локально; в CI — только проверки без ядра (см. выше). Не идеально, но 80% пользы |
| Нет CI вообще | Хуки локально (режим `warn`) + `docker/update.sh` для единых версий. Проверки на машине разработчика |
| Команда не хочет обязательных проверок | Режим `warn` (дефолт) или `off`; каждый включает `block` для себя. Знания в скилле работают в любом режиме |
| Не хотят выносить код в PSR-4-классы | Ступень 2 + ast-grep/N+1-guard (они работают по файлам, а не по namespace). Deptrac тогда не применим — это ок |
| Легаси, PHPStan захлёбывается | Два конфига: legacy — level 1 + baseline; новый код — level 6. Никто не чинит 10 лет истории |
| Нет приватного Packagist/registry | Вариант A + ядро из бэкапа; воспроизводимость — через фиксацию версии в `version-stack.toml` |
| Монорепо не нужен | Вариант A на каждый сайт + общий приватный слой настроек |

**Правило:** любая ступень лучше нулевой. Начните со ступени 2 и варианта A — это дёшево и даёт основной эффект;
остальное добавляйте, когда появится боль, которую оно лечит.
