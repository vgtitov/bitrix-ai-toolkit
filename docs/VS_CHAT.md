# Чем это отличается от обычного чата с AI

Честный ответ, без лозунгов. Если у вас уже есть корпоративный ChatGPT/другой чат и он вас устраивает — большая
часть пользы от него **реальна**, и спорить с этим глупо. Разница не в «умности модели», а в **том, что модель видит
и что делает руками**.

## Коротко

| | Чат (веб/десктоп) | Агент + toolkit |
|---|---|---|
| Видит ваш код | только то, что вы вставили | **читает файлы проекта сам**, ищет по всей базе |
| Знает ваше ядро | по памяти обучения (типовой Битрикс) | **читает ваше ядро и ваш кастомный слой** — реальные сигнатуры |
| Знает версию | нет | да (`version-stack.toml`) — не предложит API, которого у вас нет |
| Правит код | вы копипастите | **правит файлы**, показывает diff |
| Проверяет за собой | нет | прогоняет линтеры и **чинит по их выводу** до 3 циклов |
| Помнит проект | в пределах одного чата | правила и конвенции — в репозитории, действуют всегда |
| Многофайловая задача | вы собираете контекст руками | сам обходит зависимости |

## Где чат объективно не хуже (и лучше)
- **Объяснить концепцию, синтаксис, типовой Битрикс** — чат отвечает быстро и точно. Гонять для этого агента незачем.
- **Обсудить подход, накидать варианты** — удобнее в чате.
- **Разовый сниппет** — быстрее скопировать из чата.
- **Экономия** — чат не тратит токены агентской сессии.

Разумная схема: **думать и обсуждать — в чате, делать в коде — агентом.** Это не конкуренты.

## Где разница принципиальна

### 1. Ваш кастомный слой
Чат знает типовой Битрикс. Про namespace вашего подрядчика он **не знает ничего** — его не было в обучении.
Он либо честно скажет, либо предложит битриксовый аналог там, где у вас свой метод.
Агент **грепает их код** и отвечает по факту.

### 2. Версия ядра
«Этот метод есть в вашей версии?» — чат ответить не может: он не видит вашу сборку.
Агент видит: PHPStan на реальном ядре скажет «Call to an undefined method», а `deprecation-rules` — что метод устарел
(ядро само размечено `@deprecated`).

### 3. Цикл «правка → проверка → исправление»
В чате цикл замкнут на вас: скопировал → вставил → запустил → вернулся с ошибкой → скопировал снова.
У агента после каждой правки автоматически отрабатывают линтеры, и он **чинит по их выводу сам**, не тратя ваше время.

### 4. Задача на несколько файлов
«Добавь свойство и протащи его в компонент, шаблон и обмен» — в чате вы собираете контекст руками и рискуете
получить правку, не согласованную между файлами. Агент обходит их сам.

### 5. Постоянные правила
Договорённости («правки только в `/local`», «структура — миграциями», «не выбирать все свойства в списке») в чате
живут до конца сессии. В toolkit они лежат в репозитории и применяются **всегда, у всех, без напоминания**.

## Проверьте сами — три запроса

Возьмите свой проект и задайте один и тот же вопрос чату и агенту:

1. **«Какие параметры принимает метод `<класс из namespace подрядчика>::<метод>` и где он используется?»**
   Чат: не знает такого класса. Агент: находит определение и все вызовы.

2. **«Есть ли в нашей версии ядра метод X и не устарел ли он?»**
   Чат: ответ по памяти, без привязки к вашей сборке. Агент: ответ по вашему ядру + пометка deprecated.

3. **«Найди в нашем коде места, где запрос к БД идёт в цикле»**
   Чат: не может — не видит код. Агент: список файлов и строк за секунды.

Если по этим трём вопросам разницы не окажется — значит, toolkit вам действительно не нужен, и это нормальный вывод.

## Честные ограничения агента
- **Лимит сессии.** Плотная работа расходует окно; см. `docs/token-economy.md` (приёмы экономии и что делать,
  когда окно кончилось).
- **Настройка.** Чат работает сразу; агенту нужно один раз показать ядро и поставить пару инструментов.
- **Не «пишет за вас».** Правку принимает человек. Агент ускоряет рутину и ловит ошибки, но ответственность
  за код остаётся на разработчике.
